1. 为什么需要操作系统

打开任务管理器,你可能同时看到两三百个进程,但 CPU 可能只有 8 个核心;想手动控制风扇转速,Windows 却告诉你驱动装不上(09 章);打开一个"网络驱动器",文件像是就在本地,其实数据在旁路由 192.168.1.2 上(06/07 章)。这些现象共同的答案是同一句话:操作系统 = 硬件的总管 + 应用程序的看门人——它不生产任何资源,只负责把一份有限的硬件(CPU、内存、磁盘、网卡……),安全、公平地分给一堆互相并不信任的程序使用。

拆开看,这件事分四块,也是本章四节的主线:

  • 共享 CPU——几个核心怎么"同时"服务几十上百个程序 → 进程 / 线程 / 调度(第 2 节)
  • 共享内存——每个程序怎么以为自己独享全部内存,又互相看不到对方的数据 → 虚拟内存 / 分页(第 3 节)
  • 共享存储——磁盘上一串编号的扇区,怎么变成"文件"和"文件夹" → 文件系统(第 4 节)
  • 共享硬件访问权——程序想读文件、发网络包,得先"打申请"而不是想干嘛就干嘛 → 系统调用 / 中断 / 内核态 / 驱动(第 5 节)

几乎每一节都在讲同一个动作:抽象——把一份丑陋、有限、危险的硬件,包装成一份干净、看似无限、安全的假象,再想办法让这份假象足够逼真,好让程序完全不用操心底下到底发生了什么。

2. 进程与线程:虚拟出来的"专属 CPU"

没有操作系统的话,一个程序跑起来就会一直占着 CPU,直到它自己退出——那就没法一边编译代码一边听歌。操作系统用进程(process)把"一个正在运行的程序"包装成一个可以随时暂停、随时恢复的独立单元,再用调度(scheduling)在进程之间来回切换,快到你完全察觉不到。

进程的"机器状态"包含什么?按经典定义(参见 OSTEP《Operating Systems: Three Easy Pieces》):地址空间(代码、数据、堆、栈)、寄存器上下文(程序计数器 PC、栈指针 SP 等)、以及打开的文件描述符等 I/O 状态。操作系统用一块数据结构——进程控制块(PCB, Process Control Block)——把这份状态存起来:切换进程时,只需要把旧进程的寄存器存进它的 PCB,再把新进程 PCB 里存的值装回 CPU,就能造出"CPU 同时服务好几个人"的假象。一个进程在生命周期里会在几种状态之间转换(见图 1)。

进程和线程(thread)常被混着说,但边界很清楚:一个进程可以有多个线程,线程是调度的最小单位,共享同一个进程的地址空间(代码段、堆、全局变量),但各自有独立的栈和寄存器。共享内存让线程之间通信极快——直接读写同一块内存就行;代价是一个线程写坏了内存,可能拖垮整个进程。进程之间地址空间彼此隔离,一个崩溃通常不牵连另一个——这正是 Chrome / Edge 把每个标签页做成独立进程的原因:一个网页崩了,最多损失那一个标签,浏览器本体和其他标签安然无恙。

维度进程 Process线程 Thread
地址空间独立,互相隔离共享所属进程的地址空间(代码/堆/全局变量)

调度算法决定"下一个轮到谁"。Linux 历史上默认的调度器叫 CFS(Completely Fair Scheduler,完全公平调度器),由 Ingo Molnar 实现、2007 年合入 2.6.23 内核,一直用到 2023 年。它的核心思想一句话说完:模拟一个"理想的、能把 CPU 切成无限细的时间片、让所有可运行任务同时按 1/n 速度并行推进"的虚拟硬件。做法是给每个任务记一个虚拟运行时间(vruntime)——它已经用掉的 CPU 时间,并用一棵红黑树(red-black tree)把所有可运行任务按 vruntime 从小到大排序;调度器永远挑"最左边"、也就是 vruntime 最小(欠账最多)的任务运行。这个任务跑一会儿,vruntime 涨上去,自然就轮到下一个"欠账户"——CFS 因此得名"完全公平"。不过 Linux 从 6.6 内核(2023 年,Peter Zijlstra 提出)起,已经把默认调度器从 CFS 换成了 EEVDF(Earliest Eligible Virtual Deadline First)——EEVDF 沿用了 vruntime 式公平记账的核心思路,但引入"虚拟截止期(virtual deadline)"与"资格(eligibility)/lag"概念,让延迟敏感任务的响应更快。CFS 仍是理解这套公平调度思想、也是 408 统考最常考的入门模型,下面先讲它的机制。

原理 · 408 常考调度算法速览

CFS/EEVDF 是"Linux 历年真的在跑的算法"(见上文),但 408 统考更爱考这几个经典算法,搞清楚谁在优化什么:

算法核心规则优点 / 缺点
FCFS 先来先服务谁先到谁先跑,跑完才轮下一个简单公平,但一个长任务能把所有人堵死(护航效应)

实战锚点 · 你在 08 章看到的"服务",本质都是进程

08 章里打开 services.msc 看到的每一行 Windows 服务、任务管理器里几百个条目,底层都是本节讲的进程 / 线程抽象。PowerShell 里一行命令就能看到调度器在忙什么:

Get-Process | Sort-Object CPU -Descending | Select-Object -First 5 Name, Id, CPU, Threads

这行命令列出的 Threads 列,就是每个进程里当前有多少个调度单位在跟别的进程抢 CPU;chrome.exe 常常一次占好几个 PID,正是"每个标签页一个独立进程"的直接体现。

3. 虚拟内存与分页:每个进程的"专属内存"假象

如果程序直接读写物理内存地址,会有两个大问题:①两个同时跑的程序一言不合就会踩到对方的数据,甚至能读到别的程序里的密码;②程序编译时就得预先知道自己会被装进内存的哪个具体位置——这在多任务系统里根本没法保证。操作系统的解法是虚拟内存(virtual memory):每个进程看到的地址都是假的虚拟地址(virtual address),由硬件的内存管理单元(MMU, Memory Management Unit)实时翻译成真实的物理地址(physical address),程序自己完全不需要知道、也看不到这层翻译。

翻译靠分页(paging)实现:把虚拟地址空间切成一个个固定大小的页(page)(x86-64 常见 4KB),物理内存也切成同样大小的页框(frame);页表(page table)就是"页号 → 页框号"的映射表,每个进程一张。问题随之而来:页表本身存在内存里,查一次页表等于多访问一次内存,直接把开销翻倍。硬件的解法是翻译后备缓冲区(TLB, Translation Lookaside Buffer)——一块专门缓存"最近翻译过的页号 → 页框号"的小型高速缓存,命中(hit)就直接给结果(接近 1ns),未命中(miss)才去查主存里的完整页表。打个比方:TLB 就像你把最近查过的几个电话号码写在手边的便签上——要用时先看便签(TLB),便签没有才去翻整本通讯录(页表)。

再往下一层是按需分页(demand paging):程序启动时,操作系统不会把它所有的页一次性搬进物理内存——那样内存根本不够用,而是"用到哪页才调哪页"。第一次访问一个还没调入内存的页,会触发缺页中断(page fault):CPU 陷入内核,操作系统找一个空闲页框、从磁盘把数据读进来、更新页表,再让程序从刚才失败的指令重新执行——整个过程对用户程序完全透明。

这里有一笔账值得算清楚(参考 UIC 操作系统课程讲义,依据 Silberschatz 等《操作系统概念》):设一次正常内存访问约 200ns,一次缺页(牵涉一次磁盘 I/O)约 8,000,000ns(8ms);缺页率只要 p = 0.001(千分之一),有效访问时间就变成 (1−p)×200 + p×8,000,000 ≈ 8,199.8ns——单单千分之一的缺页率,就把系统拖慢了约 41 倍。反过来,要把这个拖慢控制在 10% 以内,缺页率必须低于百万分之 2.5,大约每 40 万次内存访问才允许错 1 次。这也是"内存不够、疯狂缺页"会让电脑卡到像是死机的根本原因——这个现象叫抖动(thrashing),见下方避坑。

避坑 · 电脑"卡到像死机"但 CPU 占用不高?——抖动

物理内存不够、又同时开了太多程序时,操作系统被迫不停地把这个进程的页换出、那个进程的页换入,每次切换都要等一次 8ms 级别的磁盘 I/O——这个现象叫抖动(thrashing)。诡异的地方在于:任务管理器里 CPU 占用可能并不高(因为大部分时间 CPU 根本没在算东西,而是在等磁盘),但系统对输入完全没反应。判断依据不是"CPU 是不是 100%",而是磁盘 I/O 灯是不是狂闪、"已提交内存"是不是远超物理内存——解法只有一个:关程序腾内存,或者加内存,没有调度算法能把物理内存不够这件事"调"没。

深挖 · 存储器延迟阶梯,拿真实数字感受"慢 4 万倍"有多慢

Google 工程师 Jeff Dean 整理、Peter Norvig 补充的这张"程序员应该知道的延迟数字"清单,是理解"为什么缺页这么贵"最直观的参照系:

操作大致耗时相对 L1 缓存
L1 缓存访问0.5 ns基准 1×
L2 缓存访问7 ns约 14×
主存(RAM)访问约 100 ns约 200×
SSD 随机读 4KB约 150,000 ns(150 µs)约 30 万×
机械硬盘寻道(缺页典型代价)约 10,000,000 ns(10 ms)约 2000 万×

数字每年会随硬件更新略有变化,但阶梯的数量级关系几十年没变过——这也是为什么 12 章讲 CPU cache 时,"减少一次内存访问"永远是性能优化的头号话题。

点击展开:为什么页表要做成"多级",而不是一个大数组

最直接的想法是给每个虚拟页号建一条页表项,存成一个大数组。问题是 64 位地址空间理论上有巨量页——直接摊开这张表,光页表本身就要占掉远超实际物理内存的空间,而且绝大多数进程根本用不到地址空间里的绝大部分区域。解法是多级页表(multi-level page table):把页号本身再拆成几段,一级一级地查,像查字典先翻到"某个字母开头的分卷"再往下翻页码——某一段地址范围完全没用到,对应的整段子页表可以干脆不分配。代价是多访问几次内存(每多一级就多一次查表),TLB 命中率高的话这点开销大多被吃掉,这也是为什么 TLB 命中率是现代 CPU 性能的关键指标之一。

所以实际的未命中代价比正文说的"翻倍"还要高——x86-64 常见用 4 级页表,意味着最坏情况下一次 TLB 未命中要顺序多付出 4 次而不是 1 次内存访问,这也是为什么 TLB 命中率对现代 CPU 性能格外关键。

4. 文件系统:从裸扇区到文件目录树

硬盘或 SSD 本身只认识一串编号的块(block),完全不知道"文件""文件夹""权限"这些概念——这些全部是操作系统在裸设备上叠的一层抽象,就是文件系统(file system)。07 章已经讲过 ext4、exFAT、NTFS 三种具体实现的内部差异,本节讲的是操作系统怎么让它们"看起来用法一样"。

Linux 用虚拟文件系统(VFS, Virtual File System)这一层,把千差万别的具体文件系统——ext4、NTFS、exFAT,乃至网络文件系统 SMB/NFS——统一到同一套 open()/read()/write()/close() 系统调用接口下;应用程序完全不需要关心底层到底是哪种文件系统,VFS 替它把请求转发给正确的具体实现(见图 3)。

VFS 的核心数据结构值得记住两个:inode(索引节点)存一个文件的元数据——权限、大小、时间戳、指向数据块的指针,但不存文件名;文件名存在目录项(dentry, directory entry)里,一个目录项指向一个 inode。这个设计直接解释了硬链接(hard link)的原理——见下方深挖折叠。

实战锚点 · SMB 网络盘,其实是 VFS 在"演戏"

06 章里,你在 Windows 上把 iStoreOS 旁路由(192.168.1.2)的共享文件夹映射成 Z: 盘,双击打开时感觉和本地磁盘毫无区别。这正是 VFS 抽象的效果:Windows 侧,SMB 客户端伪装成一种"文件系统驱动",接住你发出的 open()/read() 请求;实际数据请求经网络转发到旁路由,由旁路由上真正的 ext4(见 07 章)处理完,再把结果原路送回——应用程序(资源管理器、Word)全程不知道、也不需要知道对方是通过网络协议、而不是本地磁盘控制器伺服的。

点击展开:硬链接 vs 软链接,一次说清 inode 和 dentry 的关系

硬链接(hard link):两个不同的文件名(两个 dentry)直接指向同一个 inode。删掉其中一个名字,文件数据本身不受影响,直到指向它的最后一个名字也被删除,数据才真正释放——这也是为什么 rm 在 Unix 世界里字面意思是"移除一个名字",而不是"删除数据"。软链接/符号链接(symbolic link)不同:它自己是一个独立的、拥有自己 inode 的小文件,内容只是"另一个路径字符串";访问它时系统会重新解析这个路径,如果目标被移动或删除,软链接就会失效变成"断链"。硬链接不能跨文件系统(因为 inode 编号只在同一个文件系统内有意义),软链接可以随便跨,这也是两者选型时最实际的判断依据。

5. 系统调用、中断与内核态:程序怎么"借用"硬件

如果任何程序都能直接读写硬盘扇区、直接操作网卡寄存器,会出两个大问题:程序之间互相打架(两个进程同时乱写同一个扇区),以及程序能绕过所有权限检查为所欲为。操作系统的解法是把硬件访问权"收归国有":CPU 至少提供两种特权级别——用户态(user mode)和内核态(kernel mode)(x86 术语里叫 ring,常见操作系统只用 ring 3 和 ring 0,09 章见过更完整的五环模型)。用户态代码被硬件禁止执行特权指令——直接改页表、屏蔽中断、访问任意 I/O 端口——只有内核态才有全部权限。

程序想借用内核能力(读文件、发网络包、申请内存)时,要执行一条特殊指令主动"陷入"(trap)内核——这就是系统调用(system call)。经典实现是 x86 的软中断指令 int 0x80,现代 x86-64 用更快的专用指令 syscall;不管哪种,效果都一样:CPU 切换到内核态、跳到内核里对应的处理函数,办完事再把控制权和结果还给用户态程序。

/* 用户态视角:read() 看起来就是个普通函数调用 */
ssize_t n = read(fd, buf, count);

/* glibc 包装之下,x86-64 Linux 实际发生的事(简化) */
mov  $0, %rax      /* 0 = sys_read 的系统调用号 */
syscall             /* 主动陷入内核,CPU 切到 ring 0 */
/* ← 内核态:sys_read() 读取数据,准备好返回值 */
/* 处理完毕,CPU 切回用户态(ring 3),read() 正常返回 n */

系统调用是程序"主动申请";中断(interrupt)则是硬件在"被动打断"——网卡收到数据包(呼应 10 章网络分层里"数据怎么从物理层一路往上走")、键盘被按下、磁盘读操作完成,都会让硬件向 CPU 发一个信号,CPU 暂停当前正在跑的用户态代码,跳到对应的中断服务例程(ISR, Interrupt Service Routine)处理,处理完再把 CPU 还给被打断的程序,全程用户程序毫无感觉。这正是"一边下载一边打字"毫不冲突的原因:每收到一个网络包就是一次中断,操作系统抢回 CPU 处理几十微秒,再还给你正在用的程序。

维度系统调用 System Call中断 Interrupt
触发方用户态程序主动执行(如 syscall 指令)硬件设备主动发出信号
主动 / 被动主动:"我要用内核功能"被动:"CPU,你被叫走了"
典型例子read() / write() / fork() / mmap()网卡收包、键盘按键、定时器到期、磁盘 I/O 完成
处理者内核里对应的系统调用处理函数中断服务例程 ISR

补充:缺页(第 3 节)严格说是第三类——异常(exception/fault):像中断一样是被动触发,但触发源是 CPU 自己(执行指令时发现问题),而不是外部硬件;408 教材通常把它并入"中断"讲,这里沿用惯例,但要知道有这层区别。

驱动(driver)是内核里专门"认识某个具体硬件寄存器怎么读写"的代码模块——把千奇百怪的硬件差异封装成操作系统统一的接口,应用程序不需要知道自己的网卡是哪个厂商、风扇由哪颗嵌入式控制器(EC)管理。这正是 09 章"为什么 DellFanCmd 被 Secure Boot 拦下"的根因。

实战锚点 · DellFanCmd 被拦,拦的就是"进内核态"这一步

09 章讲过,DellFanCmd 这类工具想手动控制风扇转速,必须直接读写嵌入式控制器(EC)寄存器——这件事用户态程序没有权限做,只能靠一个能跑进 ring 0 的内核驱动代劳。放到本章的坐标系里说:它需要的不是"一次系统调用"就能满足的能力(读文件、发网络包这些标准操作内核早就准备好了现成的系统调用),而是要加载一整个新的内核态驱动,直接获得操作硬件寄存器的权限。问题也出在这——一旦这个驱动跑进内核态,它就拥有了操作系统的全部权力;如果驱动本身有漏洞或未经审查,相当于把 ring 0 的钥匙直接交给了任何能触发这个漏洞的人。Secure Boot + 驱动签名强制,本质上就是在回答"谁有资格把代码放进内核态"这个问题,代价是牺牲了一部分"老工具/小众工具能不能跑"的自由度。

深挖 · 内核态/用户态的隔离,曾经被硬件本身"击穿"过

内核态和用户态的隔离,理论上是硬要求——用户态程序不该有任何办法窥探内核内存或别的进程的数据。2018 年 1 月公开的 Meltdown(CVE-2017-5754) 和 Spectre(CVE-2017-5753 / CVE-2017-5715) 打破了这个假设:它们利用现代 CPU 为了跑得快而做的预测执行(speculative execution)——处理器会在还不确定某个分支/权限检查是否通过之前,提前把后续指令"猜着"执行掉,执行结果虽然最后会被撤销,但执行过程中悄悄改变的 CPU 缓存状态没有被完全清理,攻击者能通过精心测量缓存访问时间,把本该被权限检查挡住的内核内存内容,一个比特一个比特地"猜"出来。这次事件几乎影响了过去二十年生产的所有主流 CPU,修补以性能损失为代价(部分场景变慢几个百分点到几十不等),也是 15 章讲侧信道攻击时最常举的例子。

6. 避坑:三个常见误解

把前五节串起来,操作系统这一套"抽象 + 翻译"的把戏很容易在几个地方被想当然地误解,挑三个最常见的说清楚。

避坑 · "以管理员身份运行" ≠ 进了内核态

08 章讲过的 UAC 提权,弹出的那个"是否允许此应用对你的设备进行更改",只是把一个用户态进程的权限从普通用户提到管理员——它依然是 ring 3 的用户态代码,只是能做的事情更多(改系统文件、写受保护的注册表项)。它和内核态(ring 0)是完全不同的两条轴:管理员权限的用户态程序,一样要靠系统调用向内核"申请"资源,一样进不了 ring 0;真正能让代码运行在 ring 0 的,只有通过签名验证的内核驱动(见第 5 节和 09 章)。把"管理员权限"和"内核态"混为一谈,是操作系统课上最常见的认知混淆之一。

第二个误解是"杀掉一个进程,资源立刻全部释放"。在类 Unix 系统里,一个子进程退出后,它的部分退出状态会保留,直到父进程调用 wait() 读取——这段等待期内的子进程叫僵尸进程(zombie process);如果父进程自己先退出而没善后,这个子进程就变成孤儿进程(orphan process),被过继给 1 号进程(init)接管。任务管理器 / ps 里那些占着一个 PID、CPU 却是 0 的诡异条目,十有八九是这类没被"收尸"的进程。

第三个误解是"内存用得越少越好"。事实上,操作系统会主动用空闲内存做页缓存(page cache)——缓存最近读过的文件内容,这样下次读同一个文件不用再等磁盘。这就像图书馆把刚还回来的书暂放在柜台而不急着塞回书架——你要是马上又来借,直接从柜台拿走比重新去书架翻快得多;书架(其他程序)真的需要地方时,柜台上的书随时可以让位。任务管理器里"已用内存"看着很高很正常,只要"可用"里那部分本质是缓存,操作系统需要时会立刻把它让给别的程序用。真正该关心的是有没有频繁缺页 / 抖动(见第 3 节),而不是那个"已用内存"的数字本身。

本章要点
  • 进程是资源隔离的单位(独立地址空间),线程是调度的最小单位(共享地址空间);Linux 2007–2023 年默认调度器 CFS 靠 vruntime + 红黑树,永远挑"欠账最多"的任务运行(现由 EEVDF 取代,见正文)。
  • 虚拟内存让每个进程都以为自己独享全部内存,页表 + TLB 做地址翻译,按需分页省内存,但缺页代价是命中的 4~8 万倍,缺页率必须控制在百万分之几以内。
  • 文件系统把裸的磁盘块包装成文件和目录;Linux 的 VFS 让 ext4/NTFS/exFAT/SMB 在同一套系统调用接口下互换,inode 存元数据、dentry 存文件名。
  • 内核态是硬件访问权的唯一入口;系统调用是程序主动申请(trap),中断是硬件被动打断;驱动是内核里认识具体硬件的翻译官——这正是 09 章 Secure Boot 拦驱动的理论根基。
