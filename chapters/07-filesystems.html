文件系统:名字如何变成磁盘上的字节

从 inode、日志(journaling)到 ext4 / exFAT / NTFS 的选型与踩坑——搞懂"文件"这个每天要用几百次的抽象,底层到底在做什么。

← 返回首页 · 第 07 章 · 文件系统

你在 Windows 上把桌面文件拖进 E 盘,SSH 进旁路由看日志,把一个 6 GB 的系统镜像拷进 U 盘——这些动作背后都要经过同一层看不见的翻译:文件系统。它把"一个叫 report.pdf 的文件"这个人类概念,翻译成磁盘上"从哪个位置开始、连续多少字节、属于谁、什么时候改过"这类纯字节记账。看懂这层翻译,才能看懂"为什么 Mac 插 NTFS 盘只能读不能写""为什么 U 盘装系统镜像非要 exFAT 不可""为什么断电重启文件系统一般不会烂掉"这几个几乎人人都撞过的问题。

为什么文件系统不只是"一堆字节"

硬盘或 SSD 本身只提供一种能力:按编号读写一个个固定大小的扇区(block device)。它不知道"文件"是什么,也不知道哪一段字节属于谁。文件系统是操作系统内核里的一层软件,建在裸扇区之上,对外提供"文件名 / 目录 / 权限"这套人类友好的抽象,对内维护一本活账本,记录每个文件占用哪些扇区、多大、属于谁、什么时候被改过。

这本账本要解决三件事,也是本章接下来三节的顺序:

  1. 按名字找到内容——目录把文件名翻译成账本编号(inode 号)
  2. 记住内容散落在磁盘哪些角落——inode 里的指针
  3. 断电 / 崩溃时账本不能烂——日志(journaling)

类比一下:把整块磁盘想成一栋没有门牌号的仓库,文件系统就是仓库管理系统——给每捆货物发一张"货位卡"(inode),在前台登记簿(目录)上写"客户报的名字 → 货位卡编号";出入库前先在流水账(日志)上记一笔再动手搬货,这样即使搬到一半停电,翻流水账就知道该补哪一步、该扔哪一步,不用把整个仓库翻一遍清点。

核心机制一:inode——每个文件的档案卡

在 ext4 这类类 Unix 文件系统里,每个文件——不管是普通文件、目录还是符号链接——在磁盘上都有一条固定格式的记录,叫 inode(index node,索引节点)。inode 里记着模式(权限位)、属主 uid/gid、大小、几个时间戳,以及指向数据实际存放位置的指针——但唯独不记文件名。

文件名活在目录里。目录本质上也是一个特殊文件,内容就是一张"文件名 → inode 号"的表。你在文件管理器里看到的"文件名",只是目录这张表里的一个条目;文件真正的身份是它的 inode 号。

🎓 原理 · 408 视角

经典操作系统教材里的"索引结构"讲的正是这件事:inode 里放不下无限多个指向数据块的指针,于是用多级索引——比如 12 个直接指针指向最前面的数据块,再加一个一级间接块(存指针的指针)、一个二级间接块、一个三级间接块,逐级放大寻址范围。这本质上是数据结构里"指针的指针"在操作系统里的真实落地:用有限的固定大小 inode,寻址任意大的文件。

深挖:ext4 其实已经不用教科书那套多级间接块了

ext4 给大文件换了一种更省元数据空间的寻址方式,叫 extent(区段):一条记录不再只表示"一个数据块在哪",而是表示"从某个块号开始,连续 N 个块都属于这个文件"。一个几百 MB 的连续文件,用传统多级间接块可能要记录几万个指针,用 extent 可能只需要几条"起点+长度"记录。ext4 的 inode 里有一个专门的标志位(EXT4_EXTENTS_FL)标记这个文件是否用 extent 寻址;可以用 lsattr 直接看到——现代 ext4 新建文件默认就是 extent 格式,教科书里的纯多级间接块方案更多是历史沿革(ext2/ext3 时代)和"垫底兼容"用途。这是"课本理论"和"工业界实现"经常出现的一类差异:原理不变,具体编码方式会被效率驱动持续替换。

核心机制二:日志(journaling)——防止崩溃搅乱账本

更新一个文件往往要同时改好几处账本:inode 的大小字段、位图(bitmap)里标记"这块被占用了"、还有数据块本身内容。这些是分开的磁盘写入,而磁盘一次只能落一笔。如果写到一半突然断电——先写的部分留在磁盘上,后写的部分丢了——账本和实际数据就会对不上:可能位图说某个块被占用,却没有任何 inode 指向它(空间泄漏);也可能 inode 指向一个位图说"空闲"的块(读到垃圾,或被别的文件覆盖)。

老办法是 fsck:开机时把整块磁盘扫一遍,靠交叉核对把账本修平——盘越大扫得越久,对现代动辄几百 GB 到几十 TB 的盘几乎不现实。

日志(journaling,也叫 write-ahead logging,直接借用了数据库那一套)换了个思路:真正动手改账本前,先把"我准备做什么"完整写进磁盘上一块专门的日志区,写完打一个提交(commit)标记。恢复时只需要看日志里有没有提交标记:没有就整笔撤销(当它没发生过);有就把日志内容重放(replay)一遍,不用扫整块磁盘。

ext4 用的日志模块 jbd2 是从 ext3 原本的 jbd 演进而来的(后来 ext3 也换用了 jbd2),默认模式是 data=ordered:元数据(inode、位图)一定走日志,而文件的实际内容会在对应元数据提交日志之前先落盘,这样 inode 就不会指向一块还没写好的垃圾数据。还有更快但更不安全的 data=writeback(数据和元数据顺序不保证,崩溃后可能在文件里看到旧数据),以及更慢但把数据也整个走日志的 data=journal(最安全)。这个日志本身就是文件系统里一个隐藏的普通文件——ext4 里它通常固定是 8 号 inode,连"账本"自己也要有一张档案卡。

⚠️ 避坑

日志只保证文件系统结构不损坏(目录、权限、大小这些账本条目),不等于你的每一次 write() 都被当成事务写日志——默认 ordered 模式下,崩溃前几秒钟没来得及落盘的数据内容依然可能丢失。日志防的是"文件系统本身变得无法挂载",不是"帮你自动保存"。

核心机制三:扩展属性(xattr)——给文件贴标签

inode 里的字段是文件系统设计时就定死的格式:权限、大小、几个时间戳,一个萝卜一个坑,想再塞一个新字段就得改整个磁盘上的记录格式。但操作系统需要给文件挂的"标签"层出不穷,而且形状各不相同——SELinux 要挂安全上下文,POSIX ACL 要挂一整套比传统权限位精细得多的规则,用户自己也想标记"已读"这类私有信息。inode 这种固定格式的档案卡装不下无限增长的新字段,ext4 于是留了一个通用的逃生舱口:扩展属性(extended attributes,xattr)。

xattr 本质是任意的 key=value 标签,优先挂在 inode 记录后面剩余的空间里,装不下时挂到专门分配的一个数据块上。典型用途包括前面提到的 SELinux 安全标签、POSIX ACL,以及用户自己用 user.* 前缀存的任意元数据。

存放位置触发条件容量与代价典型内容
inode 尾部预留空间(in-inode)标签总大小塞得进 inode 剩余字节不占额外数据块,读取免一次寻址,但空间很小(通常几十到一百多字节)单条短标签,如 user.reviewed=yes
外部数据块(external block)标签总大小超过 inode 剩余空间额外分配一个数据块存放,容量大得多,代价是多一次磁盘读取完整 POSIX ACL 规则集、较长的 SELinux 上下文
 
# 查看/操作 ext4 的文件属性(不是 xattr,是更底层的 chattr 标志位)
$ lsattr photo.jpg
---------------e-- photo.jpg      # e = extents(区段寻址),ext4 新文件默认如此

$ sudo chattr +j important.db     # 对这一个文件单独打开「数据也走日志」

# 查看/设置真正的扩展属性(xattr)
$ getfattr -d config.yaml
$ setfattr -n user.reviewed -v "yes" config.yaml

三大文件系统怎么选

理解了 inode / 日志 / xattr 这三块机制,再看主流文件系统的差异,就是"这三块机制各自有没有、强不强"的排列组合问题。

一句话版:ext4 功能最全但只有 Linux 系不原生认;NTFS 功能同样齐全但 macOS 只给只读;exFAT 什么高级功能都没有(没日志、没权限位),换来的是三大平台都能原生读写,专门为"移动存储互通"这个场景而生;FAT32 兼容性最古老但被 4 GB 单文件上限硬卡死。

跟着做:go-bag U 盘为什么必须 exFAT

本次运维搭建的「个人运维 go-bag」是一个 Ventoy 多启动 U 盘:根目录只放 Files / Toolkit / ventoy 三样,系统 / 工具 ISO 可以放在任意深度让 Ventoy 递归扫描到。这个 U 盘要能在运维现场遇到的任何一台机器上工作——可能是 Windows 笔记本,可能要在 macOS 上读文件,还可能拔到那台跑 iStoreOS 的旁路由上应急传文件。

🛠 实战锚点

本次实测:Ventoy 的目录规则很挑——ventoy.json 配置文件必须放在 /ventoy/ 目录下(官方硬编码的固定路径,不能放根目录),而系统 / 工具 ISO 反而可以放在 /ventoy/ 之外的任意深度子目录,Ventoy 开机菜单会自己递归扫描找到它们。这类"目录结构有隐藏规则"的坑,往往比文件系统格式本身更容易踩。

格式化这个 U 盘时,三种选择的实际后果:

  • 选 NTFS(很多 Windows 格式化对话框的默认建议):Windows 自己用没问题,但插到 Mac 上只能读,不能新增、删除、重命名任何文件——包括往里面补一个新工具脚本都做不到,现场很被动。
  • 选 FAT32:Windows 的格式化对话框对 32 GB 以上的盘甚至直接不给 FAT32 这个选项;就算用第三方工具强行格式化成功,常见的系统安装 ISO 动辄 5–6 GB,拷贝到 4 GB 那一刻直接报错"文件过大,无法复制到目标文件系统"——这不是驱动没适配,是 FAT32 用 32 位字段记录文件大小,协议级地卡死在 4,294,967,295 字节。
  • 选 exFAT:Windows / macOS / Linux(含 iStoreOS 这类嵌入式 Linux,靠内核自带的 exFAT 驱动配 exfatprogs 工具,或独立的 exfat-fuse)三边都能原生读写,单文件上限扩展到 64 位字段能表示的范围,6 GB 的 ISO 直接拖进去,Ventoy 装完就能用。
# Windows(PowerShell,以管理员身份)
Format-Volume -DriveLetter F -FileSystem exFAT -NewFileSystemLabel "GOBAG"

# macOS(终端)
diskutil eraseVolume ExFAT "GOBAG" /dev/disk4

# Linux / iStoreOS(需已安装 exfatprogs)
mkfs.exfat -n GOBAG /dev/sdb1
⚠️ 避坑

exFAT 万金油归万金油,但它没有日志、没有 Unix 权限位——不要拿它当 Linux 的系统盘、Docker 数据卷,或者存"正在持续写入的数据库文件"。go-bag 里 exFAT 分区只用来存放只读的 ISO / 工具二进制,真正跑起来的操作系统(不管是 Ventoy 引导起来的哪个发行版)依旧装在它自己的 ext4 或其他原生文件系统里——exFAT 的角色始终是"跨平台的搬运工",不是"跑系统的地基"。

为什么你从不需要关心对面是什么文件系统

上面讨论的都是"物理设备插到另一台电脑"的场景——U 盘、移动硬盘,格式化选错了会直接读不了、写不了。但如果只是通过网络访问对方的共享文件夹呢?你通过 Windows「网络驱动器」或 macOS「访达」连到旁路由 / NAS 上的共享文件夹时,双击打开一个文件、拖动排序、看修改时间——全程不需要知道对方磁盘格式化成了 ext4、Btrfs 还是别的什么。这是因为 [[06]] SMB 协议只在"打开 / 读 / 写 / 列目录 / 改名"这类抽象操作层面通信;服务器收到请求后,由服务器本地的文件系统驱动负责把这条抽象操作翻译成它自己的 inode / 日志操作——协议报文本身根本不携带"底层是什么文件系统"这个信息。

反过来,在你自己电脑内部,操作系统内核也有一层等价的抽象,Linux 里叫虚拟文件系统(VFS),Windows 里叫 IFS(Installable File System)。有了这一层,open() / read() 这几个系统调用不用关心你挂载的是 ext4 分区还是 exFAT U 盘,内核按挂载点把调用分发给正确的驱动去处理——[[11]] 会展开讲这层抽象在操作系统整体架构里的位置。也正因为有这两层抽象(本地 VFS + 网络 SMB),"选错文件系统"造成的影响通常只局限在"能不能跨平台读写""崩溃后会不会丢数据",而不会波及你日常"双击打开文件"的体验——真正让人感到"格式化选错了"的,往往正是插到另一台电脑上才发现读不了、写不了的边界场景,呼应的正是 [[06]] 里 SMB / AirDrop / LocalSend 这类"跨平台互传"的实战踩坑。

深挖:写时复制(COW)——另一条根治思路

日志式文件系统(ext4、NTFS)的思路是"先记账再动手",崩溃了靠重放日志恢复。还有一条完全不同的路:写时复制(copy-on-write,COW)——修改数据时从不覆盖旧的那份,而是把新内容写到一块全新的空闲空间,最后用一次原子操作把"指针"从旧数据切换到新数据。旧数据在切换那一刻之前始终完整存在,所以根本不存在"写到一半崩溃变半成品"这回事——连日志重放都省了。ZFS 和 Btrfs 是这条路线最知名的两个代表,顺带天然支持"快照(snapshot)"这种功能,因为旧版本数据本来就没被覆盖掉。

🔎 拓展

macOS 自 10.13(High Sierra)起,默认盘全都换成了 APFS,而 APFS 同样是写时复制设计——这从侧面解释了苹果为什么几十年来对"支持读写 NTFS"这件事一直没什么动力:苹果自己的技术路线压根不在日志型文件系统这条线上。另外,如果你留意过安卓手机或部分路由器固件,会发现它们常用 F2FS(Flash-Friendly File System)——这是专门针对 NAND 闪存的擦写特性设计的日志结构文件系统(log-structured),思路和 COW 也有相通之处:都是尽量"只往前写、少覆盖",迎合闪存"覆盖写代价高"的物理特性。

📌 本章要点
  • ext4 = inode(元数据档案卡,不含文件名)+ 日志 jbd2(默认 data=ordered,防崩溃搞乱账本)+ xattr(挂任意 key=value 标签,如 ACL / SELinux)。
  • FAT32 用 32 位字段记文件大小,硬限制在 4 GiB(2³²−1 字节);exFAT 就是为解决这个限制而生,换成 64 位字段,代价是没有日志、没有 Unix 权限位。
  • NTFS 功能最全(日志 + ACL + 加密 + 压缩),但 macOS 自 Mac OS X 10.3 起只给只读支持,写入要靠第三方驱动。
  • 三平台互传移动存储优先 exFAT;NTFS 适合"以 Windows 为主、其它平台只读访问"的场景;ext4 留给真正跑 Linux 系统的磁盘。
  • 你几乎不需要关心共享文件夹对面是什么文件系统——本地有 VFS、网络有 SMB,两层抽象把这些差异都吸收掉了(见 [[06]] / [[11]])。
