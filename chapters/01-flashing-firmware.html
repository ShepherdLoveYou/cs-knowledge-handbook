从 Chromebox 到 UEFI:刷机与固件

一台被 Google 判了「过期」的 Chromebox,拆开来看 CPU、内存、硬盘都还年轻——真正被判死刑的,只是它头顶那一小片锁死的固件。本章拆开「刷机」这件事的三层积木:写保护、coreboot、UEFI,讲清楚一台专用设备如何变回一台普通的 x86 电脑。

为什么要刷机:一台被判「过期」的好电脑

Chromebox / Chromebook 是一类刻意把智能都放在云端和自动更新上的廉价电脑,代价是出厂那天起就写好了一个到期日。

Google 官方把这个到期日叫 AUE(Automatic Update Expiration,自动更新到期日)。过了这一天,Google 停止推送 ChromeOS 和 Chrome 浏览器的安全更新,设备照样能开机,但系统层面已经没人维护——MrChromebox 官方文档把这类机器直接称为 EOL(End of Life)设备。

问题是,到期的只是「操作系统的保修单」,不是硬件。CPU、内存、SPI Flash 芯片、网卡都是实打实的硅片,不会在某个日期集体失效。一台 2014 年 Haswell 平台的 Chromebox,算力和同代普通 x86 迷你主机没有本质区别,完全够格干很多轻量的事——比如整本手册接下来要用到的角色:一台常年开机的旁路由主机(见 [[02]] 软路由与旁路由)。

真正拦住这条路的,是写在主板 SPI Flash 芯片里的那一小段代码,也就是固件。出厂状态下它只认一件事:验证并启动 ChromeOS。「刷机」的本质,就是把这段固件换掉,换成一段谁都认的固件。这正是本章要拆开讲的内容。

🔧 实战锚点

本手册里的旁路由主机,就来自一台这样「过期」的 Chromebox。走的是 MrChromebox 官方文档里最常被引用的范例机型——ASUS Chromebox CN60(内部代号 PANTHER,Haswell 平台)——之后的标准流程:开发者模式 → 拆机移除写保护螺丝 → 刷入 UEFI Full ROM 固件 → 装 Linux 发行版。刷完之后,它就是 [[02]] 里那台旁路由主机的物理载体。

固件是什么:BIOS → UEFI → coreboot 三层积木

把固件想象成剧场的舞台监督:观众(操作系统)登场之前,得先有人确认电源、灯光、麦克风都通着,幕布挂对了位置,然后才把话筒交给主角。CPU 通电的一瞬间,内存是空的,硬盘还没被认出来,连「第一条指令去哪读」都需要有人钦定——这条钦定的路径,就藏在主板上一颗几毫米见方的 SPI Flash 芯片里,这正是固件。CPU 上电后从固定地址(复位向量)取第一条指令,是计算机组成原理里「自举」(bootstrap)问题的起点,[[12]] 计算机组成原理 会从冯诺依曼架构的角度把这一层继续往下讲。

传统 BIOS(Basic Input/Output System)是这份工作最早的标准答案,可追溯到 IBM PC 时代:16 位实模式汇编代码,做完硬件自检(POST)就把控制权交给硬盘第一个扇区里的引导代码。它撑了 30 年,但也背着 30 年前的枷锁——寻址能力有限、只能用汇编写、和 x86 深度捆绑。

UEFI(Unified Extensible Firmware Interface,统一可扩展固件接口)是 UEFI 论坛(由 Intel 发起后移交给行业联盟)定义的下一代标准:用高级语言(通常是 C)实现、模块化、按官方 FAQ 的说法「处理器架构无关」——不仅支持 x86/x64,也支持 ARM 和历史上的 Itanium。UEFI 官方 FAQ 里有一句常被误读的话值得原文引用:「UEFI 规范定义的是一个接口,而 BIOS 特指一种具体的固件实现」——也就是说,UEFI 取代 BIOS 不是简单的新版本换旧版本,而是「标准接口」取代了「一种具体做法」。

这里藏着一个反直觉的事实:coreboot 是一个开源项目,只做「让硬件能被使用」这件刚好够用的事,然后把控制权交给一个叫 payload(负载程序) 的独立模块——常见的 payload 包括提供传统 BIOS 服务的 SeaBIOS、提供 UEFI 服务的开源实现 edk2(也叫 Tianocore)、Linux 常用的引导器 GRUB2,以及 Chromebook/Chromebox 专用的验证启动引导器 depthcharge。ChromeOS 设备出厂时就已经在跑 coreboot 了——Google 没有另起炉灶,只是把 payload 换成了自家锁死的 depthcharge。所谓刷机,在多数机型上并不是把 coreboot 换掉,而是把 payload 从 depthcharge 换成 edk2:同一个地基,换一间屋子。

维度传统 BIOSUEFI

处理器架构基本绑定 x86架构无关:x86、x64、ARM、(历史上的)Itanium
分区表MBR(容量与分区数有历史局限)GPT

📐 原理 · 408 / 系统

「CPU 上电后先执行谁」在计算机组成原理里有标准答案:复位信号把程序计数器(PC)拉到一个厂商写死的固定地址(复位向量),那个地址上的代码就是固件的入口。固件做完硬件初始化后,再把控制权「移交」给下一层——这正是 payload 机制的通用形态。这条移交链(硬件 → 固件 → 引导器 → 内核 → 用户态)在 [[12]] 计算机组成原理 会配合流水线、存储层次继续展开。

🔍 深挖 · coreboot 的工程哲学

coreboot 官方文档把项目哲学写得很直白:「尽量不留驻内存」(no resident services if possible)——理想状态下 coreboot 完全交棒给 payload,自己不留一兵一卒;现实中 x86 上仍有一小段代码常驻在 SMM(System Management Mode,系统管理模式)里提供有限服务,但项目会把这部分范围压到最小。coreboot 本身不发布二进制固件,只发布源码;遇到硬件初始化必须依赖厂商私有代码(blob)的情况,会由社区评审「值不值得引入」——这也是为什么 MrChromebox、Purism 这类「发行版」要在 coreboot 之上再打包一层,才能变成普通用户可以直接刷的成品固件。

ChromeOS 的三道门:恢复模式 / 开发者模式 / 写保护

光知道 payload 可以换掉还不够快——ChromeOS 出厂时用三道相互独立的门保护自己,缺一道都进不了刷 Full ROM 固件的门。三道门各管一段,先看一眼全貌,再逐一展开:

门保护什么怎么触发 / 怎么过要不要拆机
门一:恢复模式让设备始终能回到出厂干净状态,兜底任何改坏的情况Chromebook:Esc+Refresh+Power;Chromebox:回形针捅 recovery 按钮通电不需要
门二:开发者模式验证启动(verified boot)的强制性;放开后才能拿到 root shell、改内核/根文件系统、走 Legacy Boot恢复/警告界面按 Ctrl+D,等约 5 分钟状态分区擦除通常不需要(部分早期机型的物理开关例外)
门三:写保护固件只读(RO)区能不能被重写拆下 WP 螺丝(2013–2017 世代)/ 拔电池排线(CR50 起)/ 短接跳线或 SuzyQable 走 CCD需要

门一:恢复模式(Recovery Mode)

这是「无论如何都能回到安全状态」的门:在 Chromebook 上按住 Esc+Refresh+Power,或在 Chromebox 上用回形针按住机身的 recovery 按钮通电,设备就会只信任 Google 签过名的恢复镜像,从 U 盘重新安装一份干净的 ChromeOS。按 Google 官方说明,这个操作会清空硬盘上的一切,U 盘至少需要 8GB 且会被完全抹除来制作。

折叠:官方 ChromeOS 恢复 U 盘怎么做
  1. 准备一台能装 Chrome 浏览器的其它电脑,以及一根 ≥8GB、可以被完全抹掉的 U 盘。
  2. 在这台好用的电脑上给 Chrome 装「Chromebook 恢复实用程序」(Chromebook Recovery Utility)扩展。
  3. 打开扩展,从型号列表里选中(或手动输入)故障机的具体型号,插入 U 盘并点击创建。
  4. 回到故障机,进入恢复模式(见正文按键组合),选择「使用外部磁盘恢复」,按提示走完流程。
  5. 恢复完成后设备自动重启;U 盘若要挪作他用,需要先在扩展里「擦除恢复介质」再正常格式化。

门二:开发者模式(Developer Mode)

开发者模式放松的是「验证启动」——给你 VT2 虚拟终端的 root shell、允许修改内核与根文件系统、允许通过 Legacy Boot 菜单启动其它系统,同时也是后续几乎所有固件改动的前置条件。进入方式很直白:在恢复/警告界面按 Ctrl+D。这不是随手加的彩蛋——按 Chromium 官方设计文档,这恰恰是 Google 明确批准的「开发者开关」几种实现之一(另外两种是螺丝盖下的物理开关,或者藏在电池仓里必须拆开才能碰到的开关)。

切换进/出开发者模式都会触发一次长达 5 分钟的状态分区擦除延迟,这是刻意设计:目的是把「顺手攻击一台无人看管的设备」的成本,拉高到接近「物理拆机攻击」的水平。警告界面本身也有精确的时间设计——「OS verification is OFF」白屏 20 秒后会响一声提示音,30 秒无操作则自动继续启动开发者签名的系统;按 Ctrl+D 可以立即跳过等待。

写保护更像自来水表外壳上的铅封:光有开发者模式这把「房子钥匙」,不代表你能合法拆开电表——拆封本身是另一个独立的物理动作,而且拆过就是拆过,装回去也瞒不住检查的人。

门三:写保护(Write Protection,WP)

这是真正决定「固件的只读区能不能被重写」的门,和开发者模式完全独立。它分两层:软件写保护是刷写芯片上的一组特殊寄存器,可以把若干地址区间标记为只读;而这组寄存器本身能不能被改动,又由硬件写保护——一个电路层面的开关——把关,通常做法是把 Flash 芯片的 !WP 引脚接地。

时期 / 世代硬件写保护机制如何解除
2011–2013(截至 2013 Chromebook Pixel 之前的早期机型)物理开关 / 跳线直接拨动开关
2013–2017(自 2013 Chromebook Pixel 起,CR50 之前:Haswell / Broadwell / Baytrail / Skylake / Braswell 等)一颗「WP 螺丝」把 !WP 引脚接地拆机取下螺丝(不用装回)
2017 年至今(CR50 / Ti50 安全芯片机型)安全芯片(GSC)依据电池感应线状态控制 !WP断开主板电池排线;部分新机型需短接一个未焊接的跳线,或用 SuzyQable 走 CCD 调试口
⚠️ 避坑 · 别把两道门搞混

MrChromebox 官方文档开篇第一句话就在纠偏:「写保护是 ChromeOS 设备上最常被误解的机制之一——很多教程会在讲别的操作时,顺手让你先把写保护关掉,其实完全没必要。」开发者模式 ≠ 关闭写保护,是两道独立的闸门:只有当你要改只读(RO)区——比如刷 UEFI Full ROM、或者改 GBB Flags(GBB,Google Binary Block,固件只读区里存放开发者模式启动行为标志位等数据的一块区域)——才需要关 WP;像装 RW_LEGACY 这种只动可写区域的操作,完全不需要碰写保护,更不需要拆机。

🔍 深挖 · 没有螺丝之后怎么办

2017 年后带 CR50/Ti50 安全芯片(Google 内部叫 GSC,Google Security Chip)的机型不再有物理螺丝,WP 状态改由芯片依据电池感应线判断——多数机型只要把主板上的电池排线拔掉就能让 WP 失效;部分新机型改为需要短接一个未焊接的跳线。也可以用一根特制的 USB-C 调试线(官方昵称 SuzyQable)走「闭盒调试」(Closed-Case Debugging,CCD)在不拆机的情况下切换 WP 状态。2023 年之后的 Ti50 机型还多了一层「AP RO 固件验证」,需要额外单独关闭才能刷写。这条链路正是 [[09]] 固件安全与内核驱动 要展开的信任根话题。

怎么刷:从 RW_LEGACY 到 UEFI Full ROM

MrChromebox 提供的固件更新分两条路,选哪条取决于你还要不要 ChromeOS。

对比项RW_LEGACYUEFI Full ROM
需要先解除写保护?不需要需要
ChromeOS 还能启动吗?能,双系统(开机按 Ctrl+L 切换)不能,被彻底替换
变砖风险几乎为零存在,但脚本会自动备份 MAC / VPD / HWID 降低风险
UEFI NVRAM(记住启动项)不支持支持
适合谁想双启动、不想拆机只跑 Linux / Windows,想要一台「正常 PC」
🔧 worked example · 把 Chromebox 刷成 UEFI Full ROM

以官方文档最常引用的 ASUS Chromebox CN60(代号 PANTHER)为例,走一遍完整流程:

  1. 在恢复/警告界面按 Ctrl+D 进入开发者模式,等一次约 5 分钟的状态分区擦除。
  2. 登录 ChromeOS 后按 Ctrl+Alt+F2 切到 VT2 终端,用 chronos(而不是 root)登录。
  3. 物理拆开机身,找到并取下写保护螺丝(2013–2017 世代机型;CR50 机型改为拔电池排线)。螺丝在 PANTHER 主板上的具体位置,可对照 MrChromebox 官方设备支持列表(Haswell 分类下 PANTHER 一行)里的实物照片。
  4. 以普通用户身份(不要 先 sudo su)运行官方固件工具脚本: 
    cd; curl -LOf https://mrchromebox.tech/firmware-util.sh && sudo bash firmware-util.sh
  5. 菜单里选择「Install/Update UEFI (Full ROM) Firmware」。脚本会自动识别主板型号,把当前固件里的序列号、硬件 ID(HWID)、VPD(Vital Product Data,存出厂参数的区域,含以太网 MAC 地址)、内存训练缓存(RW_MRC_CACHE)一并抽出来,注入新固件——按官方文档,保留 MRC 缓存能让刷机后第一次开机省下最多 60 秒的内存训练时间。对 Chromebox 而言,VPD 里的 MAC 地址尤其关键:漏掉这一步,网卡就会用一个重复或无效的 MAC 上网。
  6. 刷写完成、重启,设备直接进入 UEFI 界面,ChromeOS 已经不在了——这台机器现在是一台「裸机」x86 PC,可以装任何 UEFI 兼容的系统。

刷完之后,这台空白主机会在 [[02]] 软路由与旁路由 里被装上 iStoreOS,变成手册后续章节反复出现的那台旁路由。

折叠:固件工具脚本菜单里还能干什么
  • Backup Current Firmware——刷任何东西之前先备份到本地或 U 盘,文件名自动带板名/版本/日期,是出问题时唯一的退路。
  • Restore Stock Firmware——用之前的备份、或直接从官方恢复镜像里提取 shellball 还原出厂固件;EOL 设备会被脚本直接拒绝这个选项(见下方避坑)。
  • Set Boot Options(GBB Flags)——只对未刷 Full ROM 的原厂固件有效,六个选项(其中四个是等待时长 1 秒/30 秒 × 默认启动目标 ChromeOS/Legacy Boot 的组合,另外两个是恢复出厂默认与取消)。
  • Clear UEFI NVRAM——仅 Full ROM 固件下可用,清空启动项配置,常用来修复损坏的启动顺序。

避坑清单

⚠️ 避坑 · 刷写中途失败,千万别重启

官方文档原话:如果刷写过程失败,不要重启,先用「恢复」选项把备份的 ROM 重新刷回去。半途重启很可能让设备停在一个既不是旧固件、也不是新固件的中间状态,这才是真正意义上的「变砖」。这也是为什么第一步永远是「先备份」。

⚠️ 避坑 · EOL 设备拒绝恢复出厂固件,是有意为之

过了 AUE 日期的设备,脚本会直接不让你把出厂 ChromeOS 恢复回去——这不是 bug,而是故意的:恢复一个不再收到安全更新的旧系统对谁都没好处。官方建议是继续用 UEFI 固件配 Linux / Windows / ChromeOS Flex,这几个都还在持续获得更新。

其它常见误区:GBB Flags 只在原厂固件(含 RW_LEGACY)上有意义,刷完 UEFI Full ROM 之后这套机制根本不存在,继续找它设置是白费功夫;运行固件工具脚本必须用普通用户身份,脚本内部自己会在需要时调用 sudo,提前 sudo su 反而会把事情搞坏。

本章要点

📌 本章要点
  1. 固件是 CPU 上电后执行的第一段代码,分两层:硬件初始化(coreboot)+ 引导载荷(payload:depthcharge / SeaBIOS / edk2)。
  2. UEFI 是行业标准定义的「接口」,不是某个具体实现;它取代的是运行在 16 位实模式、和 x86 深度捆绑的传统 BIOS。
  3. ChromeOS 出厂时用恢复模式、开发者模式、写保护三道相互独立的门层层把关;开发者模式放松验证启动,但不等于关闭写保护。
  4. 写保护是纯硬件电路(接地 !WP 引脚),不是软件开关,所以必须物理拆机操作——这是有意的安全设计,不是历史包袱。
  5. 换上 UEFI Full ROM 固件后,payload 从 depthcharge 换成 edk2,Chromebox 变成一台可以装任何 x86 系统的裸机,为下一章的旁路由改造铺好了路。
