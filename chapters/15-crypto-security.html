1. 为什么需要密码学——三个从未消失的老问题

设想 Alice 要给 Bob 发一条消息,中间必须经过一段谁都能围观、谁都能动手脚的线路——可能是公共 WiFi(见第 04/05 章),可能是被下毒的 DNS(见第 03 章),也可能只是隔壁运营商的一条骨干链路。这条线路上,任何一个"Eve"式的窃听者都可能做三件坏事:①偷看内容,②偷偷篡改内容再放行,③冒充 Alice 或 Bob 中的一方。

密码学要解决的,从来就是这三个问题,行业里给它们起了标准名字——机密性(confidentiality,不被看)、完整性(integrity,不被改)、身份认证(authentication,认得清是谁)。TLS 1.3 的标准文档 RFC 8446 开篇就是把这三条当成协议必须提供的安全属性明文写进去的。本章接下来按"解决这三个问题分别要用什么工具"的顺序展开,最后把所有工具拼装成一次完整的 TLS 1.3 握手——你此刻打开这个网页,浏览器背后大概率就跑了一遍。

2. 一张地图:四件工具各管一段

拆开细讲之前,先看清楚整体分工——密码学里最容易搞混的,就是把"加密""哈希""签名"这三件不同的事当成一回事。下表是本章要讲的四件工具,以及各自解决第 1 节里哪个问题:

对称加密(AES)机密性:让人看不懂内容1 把,双方共享可逆(有密钥就能解密)TLS 应用层数据高速加密

3. 对称加密:一把钥匙锁两道门(AES)

为什么:解决机密性最直接的办法就是物理钥匙的思路——Alice 和 Bob 提前通过某种安全渠道约定同一把"钥匙"(密钥),Alice 用它把消息锁起来,Bob 用同一把钥匙打开。这套思路统称对称加密(symmetric encryption):加密和解密用的是同一个密钥。

怎么运作:今天几乎所有系统的默认选择是 AES(Advanced Encryption Standard,高级加密标准)——NIST(美国国家标准与技术研究院)2001 年发布的 FIPS 197 标准,选中比利时密码学家设计的 Rijndael 算法作为获胜方案。AES 是一种分组密码(block cipher):把明文切成固定大小的块,一块一块加密。FIPS 197 规定的块大小固定是 128 位,密钥可选 128/192/256 位三档,对应轮数也不同:

密钥长度块大小内部轮数
AES-128128 位128 位10
AES-192192 位128 位12
AES-256256 位128 位14
展开:AES 内部一轮到底在做什么

每一轮反复做四步变换:SubBytes(按一张固定的 S 盒替换每个字节,提供非线性)、ShiftRows(按行循环移位,打散列内关联)、MixColumns(在有限域 GF(2⁸) 上对列做线性混合,最后一轮省略这步)、AddRoundKey(与本轮密钥异或)。最初的输入先额外做一次 AddRoundKey。这套设计出自 FIPS 197,不需要记住数学细节,只要知道:每多一轮,原文的统计规律就被打散得更彻底,10/12/14 轮之后,已经找不到明文和密文之间可利用的关联。

AES 本身只加密一个固定长度的块,真正处理任意长度的数据还需要"工作模式"(mode of operation)把很多块串起来——早期的 ECB 模式(每块独立加密,互不影响)有个致命弱点:两块相同的明文永远加密成相同的密文,一张有大片重复色块的图片,加密后轮廓依然隐约可见。现代 TLS 1.3 只允许 AEAD(Authenticated Encryption with Associated Data,带认证的加密)模式,例如 AES-GCM——它在加密的同时顺手算出一个校验标签,接收方一并验证数据没被动过,机密性和完整性一次搞定,这也是 RFC 8446 明确"砍掉所有非 AEAD 算法"的原因。

怎么用/避坑:对称加密快、省资源,是所有系统处理大批量数据的实际主力——但它留了一个致命前提:双方必须已经拥有同一把密钥。这把密钥怎么第一次安全送到对方手上,而不被半路的 Eve 复制一份?这正是下一节非对称加密要解决的问题。

4. 非对称加密:两把钥匙解开老问题(RSA / ECC)

为什么:对称加密的死结在于"密钥必须先被安全共享"——可如果已经有办法安全共享一段密钥,又何必加密?这看起来是个先有鸡还是先有蛋的死循环。1970 年代,Diffie、Hellman、Rivest、Shamir、Adleman 等人给出的答案是一个数学戏法:找一种运算,生成两把不同但数学上配对的钥匙——用其中一把加锁,只有另一把才能开;而且从公开的那把,反推不出配对的另一把(至少在现实时间内做不到)。这就是非对称加密(asymmetric / 公钥加密)。

怎么运作:最经典的实现是 RSA——安全性建立在"两个大质数相乘很容易,但把乘积反过来分解回两个质数极其困难"这个数学猜想上。另一条路线是 ECC(椭圆曲线密码学),安全性建立在椭圆曲线上的离散对数问题——同样是"正向算容易,反向推极难"的单向陷门结构,但数学结构更紧凑,能用小得多的密钥做到同等强度。按 NIST SP 800-57 官方给出的密钥强度对照表:

安全强度对称密钥(AES)RSAECC
112 位3TDEARSA-2048224–255 位
128 位AES-128RSA-3072256–383 位

也就是说,一把 256 位的 ECC 密钥,安全强度大致相当于一把 3072 位的 RSA 密钥——这也是为什么 TLS 1.3、SSH 乃至新一代签名规范里,ECC(常见曲线如 P-256)正逐步替代 RSA 成为默认选择:同等安全强度下,密钥更短、运算更快、证书体积也更小。

非对称加密能反着用出两种完全不同的用途,很容易搞混,务必分清:

方向谁来"锁"谁能"开"解决什么问题
公钥加密任何人用 Bob 的公钥加密只有 Bob 的私钥能解密机密性(只有 Bob 能看懂)
私钥签名只有 Bob 的私钥能签任何人用 Bob 的公钥验证真实性 + 完整性(第 6 节详解)

类比:非对称加密像一把只能从外面按下去锁上、只有一把配对钥匙能打开的挂锁——Bob 把敞开的挂锁本体(公钥)大大方方公开散发,谁都能拿去把箱子锁上(加密),但箱子寄回来之后,全世界只有留着那把配对钥匙(私钥)的 Bob 能打开。反过来,Bob 也能用他的私钥在一份文件上盖一个独一无二的戳(签名)——这个戳谁都验证得了真伪(拿 Bob 公开发布的挂锁样式一比对就知道),但只有 Bob 能盖出来。

实际系统几乎从不用非对称加密处理大批量数据——RSA/ECC 的运算比 AES 慢上两到三个数量级。真实做法是混合加密(hybrid encryption):握手阶段用非对称加密"协商"出一段临时的对称密钥,之后大量数据仍旧靠对称加密(第 3 节的 AES)高速处理。第 9 节的 TLS 1.3 握手,骨架正是这套混合结构。

原理 · 408 网络安全考点 + 两种"安全"的区别

国内计算机学科 408 统考的《计算机网络》科目,考纲里明确列了"网络安全:安全的计算机网络/数据加密模型/常见加密算法/数字签名/鉴别/密钥分配"这一整块——本章基本上就是把这块考点系统化。这里有一个常被忽略的理论区分:密码学家把"安全"分成两种。信息论安全(如一次性密码本 one-time pad——密钥和明文一样长且只用一次,被 Claude Shannon 证明为"完美保密",即便攻击者算力无限也破不了)和计算安全(如 AES/RSA——理论上都能被穷举,只是穷举需要的时间远超现实意义)。现实世界几乎所有系统用的都是后者——密码学的安全,从来不是"绝对破不了",而是"破解代价远大于收益,或远超密钥的有效期"。

5. 哈希函数:数据的指纹

为什么:光有加密还不够——Bob 收到一份文件,想确认"这份文件真的没被人半路改过一个字节",总不能每次都拿原文完整备份逐字节比对。需要一种运算:把任意长度的输入压缩成一段固定长度的"指纹",原文只要改一个比特,指纹就面目全非;而且这运算只能往一个方向走——从指纹反推不出原文。这就是哈希函数(hash function),有时也叫摘要算法(digest)。

怎么运作:今天最主流的是 SHA-256,属于 SHA-2 家族,定义在 NIST FIPS 180-4 标准里——不管输入是一个字还是一整部电影,输出永远是 256 位(32 字节,通常写成 64 个十六进制字符)。一个合格的哈希函数要满足三条性质:

  • 确定性:同样的输入,任何时候算,输出都一样;
  • 雪崩效应(avalanche effect):输入哪怕只改一个字符,输出也像雪崩一样面目全非,看不出跟原输出有任何关联;
  • 抗碰撞性(collision resistance):找到两个不同的输入、算出同一个哈希值,在计算上必须不可行。NIST 官方强度表里,SHA-256 的碰撞抗性强度是 128 位——穷举找到一次碰撞平均要试 2¹²⁸ 次,是当前算力完全够不到的天文数字。
实战锚点 · 现在就能在自己电脑上跑一遍

在 Git Bash / macOS / Linux 终端里跑:

$ printf '%s' "Secure Boot" | sha256sum
208b86c7637b82ee891d0c3edbc15a778a4db94c2f7ea6a27f8397d56b6e0cb1

$ printf '%s' "secure Boot" | sha256sum
62953214f2f92c6882c609e1ba660849a51f03b9cc58abd7ce7a483f7e88f7eb

只把开头的 S 改成小写 s,输出的 64 个十六进制字符几乎全部不同——这就是雪崩效应的真实样子。纯 Windows cmd 环境没有 sha256sum,可以用 certutil -hashfile 文件名 SHA256 对一个文件做同样的事(certutil 只对文件算,不能直接对字符串算)。

回到第 09 章那个 Code 52 的故事:Windows 验证驱动签名时,第一步做的正是对整个驱动二进制跑一遍哈希,拿到一段"指纹"——这份指纹才是接下来要验证的对象,而不是把几 MB 的驱动文件直接拿去做非对称运算(慢得离谱)。这也是第 6 节数字签名的第一步。

深挖 · SHA-1 真的被攻破了,不是纸上谈兵

2017 年 2 月 23 日,荷兰 CWI 研究所与 Google 的团队联合公布了 SHAttered 攻击——第一次在现实中构造出两个内容不同、SHA-1 哈希值却完全相同的 PDF 文件,用的是精心计算过的内部数据,肉眼看到的是两份不同的文档,底层字节被构造成让 SHA-1 算法看不出区别。这不是理论推演,是真实可下载验证的两个文件。此后 SHA-1 被主流浏览器、Git、TLS 陆续弃用或降级——RFC 8446 干脆在 TLS 1.3 标准文本里明文禁止用 SHA-1 签署证书(除非找不到任何其他可用的证书链)。MD5、SHA-1 的教训一次次证明:哈希函数没有"绝对安全",只有"目前已知没有比穷举更快的攻破方法",而这份"目前"会过期。

哈希在局域网登录里也在悄悄干活:第 06 章要讲的 SMB/Windows 文件共享登录,底层走的 NTLM 或 Kerberos 认证协议,都不会把你的密码明文送上网——NTLM 靠一次"挑战-应答"(服务器发一个随机挑战值,客户端用密码哈希算出应答,双方比对而不传密码本身),Kerberos 则用密钥派生和对称加密(第 3 节的思路)签发一张有时效的"票据"。微软官方文档明确说 Kerberos 自 Windows 2000 起就是默认认证协议,NTLM 是保留给没有域控制器的工作组场景的后备方案,细节留给第 06 章。

6. 数字签名:哈希 + 非对称的组合拳

为什么:哈希能证明"没被改过",却证明不了"是谁发的"——任何人都能对一份文件算哈希,附上去伪装成"官方指纹"。需要把"谁都算得出但改不了"的哈希,和"只有一个人能做到"的私钥操作绑在一起。这就是数字签名(digital signature):内容完整性 + 身份真实性,一次验证两件事。

怎么运作:NIST FIPS 186-5(数字签名标准 DSS)把流程定义得很干净——私钥用来生成签名,公钥用来验证签名。具体拆成两步:

  1. 签名:先对原文算一遍哈希(第 5 节),再用签名者的私钥对这段哈希做一次数学运算,生成一段签名值,和原文一起发出去。
  2. 验证:收到方独立对收到的原文重新算一遍哈希,再用签名者公开发布的公钥"解开"签名值——如果两个哈希对得上,原文没被改过(完整性),而且这个签名只有对应私钥的持有者能生成(真实性)。

常见的具体算法有 RSA 签名(直接复用第 4 节 RSA 的数学结构反过来用)、ECDSA(基于椭圆曲线)、以及更新的 EdDSA——FIPS 186-5 是 2023 年最新修订版,首次把 EdDSA 收进国家标准,同时把老旧的 DSA 降级为"只许验证旧签名,不许再用它签新东西"。

实战锚点 · 第 09 章那个 Code 52,数学上到底发生了什么

回到 Precision 7530 上那次"无法验证此设备驱动程序的发布者":Windows 启动时,固件的 db/dbx 签名库(见第 09 章)里存的正是一组受信任的公钥或哈希。加载一个驱动前,Windows 对驱动二进制文件重新计算一遍哈希,再用驱动数字签名里带的证书公钥解开附带的签名值——两个哈希对得上、证书链(第 8 节)也验证通过,才放行进 ring 0;DellFanCmd 类工具如果没有走完整的 Microsoft Dev Center 签名流程,这一步验证失败,操作系统直接拒绝加载,报的就是 Code 52。第 09 章留了一句"数学细节见第 15 章"——这就是它说的那套验证。

数字签名也解释了第 03 章 DoH 那句"加密不等于验真"到底在说什么区别:DoH(RFC 8484)只给你和上游 DNS 服务器之间的这段传输加了一层 TLS 加密(机密性),从没对 DNS 响应内容本身盖一个签名;真正对 DNS 记录内容签名担保的是 DNSSEC——用区域(zone)自己的私钥对每条记录签名,解析器拿对应公钥验证,这才是"验真"。加密管的是"传输路上有没有人偷看/改动",签名管的是"内容本身是不是它自称的那个来源",这是两件独立的事,可以只做一件,也可以同时做。

7. worked example:手算一遍 RSA(加密与签名两个方向)

真实 RSA 的质数动辄 600 位十进制数字,没法手算;这里用两个很小的质数演示同一套数学结构,方便一步步跟着算——原理和真实 RSA 完全一样,只是数字小到能用计算器验证(下列每一步都已用 .NET 的 BigInteger 精确验证过,不是手工估算)。

  1. 选两个质数:p = 61,q = 53(真实系统里这两个数是随机生成的 600 位以上大质数)。
  2. 算模数:n = p × q = 61 × 53 = 3233 —— 这个 n 会被公开,是公钥的一部分。
  3. 算欧拉函数:φ(n) = (p−1)(q−1) = 60 × 52 = 3120 —— 这个数必须保密,只有算出 p、q 的人才能算。
  4. 选公钥指数:e = 17(只要和 3120 互质即可)。公钥就是 (n=3233, e=17)——可以公开给任何人。
  5. 算私钥指数:找一个 d,使得 e × d ≡ 1 (mod φ(n))。算出 d = 2753(验证:17 × 2753 = 46801 = 15 × 3120 + 1)。私钥就是 (n=3233, d=2753)——必须保密。
方向谁执行公式代入数字结果
加密(机密性)Alice,用 Bob 公开的公钥c = m^e mod n65^17 mod 3233c = 2790
解密Bob,用自己的私钥m = c^d mod n2790^2753 mod 3233m = 65(✓ 复原)
签名(真实性)Bob,用自己的私钥s = m^d mod n65^2753 mod 3233s = 588
验证Alice,用 Bob 公开的公钥m' = s^e mod n588^17 mod 3233m' = 65(✓ 吻合)

这里的 65 可以看成明文里一个字节的数值(ASCII 里大写字母 "A" 正好是 65)——真实场景里 RSA 几乎从不直接加密整段消息(第 4 节说过它慢),而是只加密/签名一段固定长度的对称密钥或哈希值,这也是为什么例子里的数字"刚好能装进 n 以内"不是巧合,而是真实系统里必须满足的约束(消息数值必须小于 n)。

想自己动手验证这组数字,Windows 自带 PowerShell 内置大数运算,不需要装任何东西:

$n=[bigint]3233; $e=[bigint]17; $d=[bigint]2753; $m=[bigint]65
$c = [bigint]::ModPow($m,$e,$n)          # 加密: 应输出 2790
$back = [bigint]::ModPow($c,$d,$n)       # 解密: 应输出 65
$s = [bigint]::ModPow($m,$d,$n)          # 签名: 应输出 588
$verify = [bigint]::ModPow($s,$e,$n)     # 验证: 应输出 65
"$c $back $s $verify"
避坑 · 真实 RSA 绝不会用这么小的数字

这个例子里 n = 3233,分解成 61×53 用一台家用电脑瞬间就能算出来——现实中的 RSA 必须用至少 2048 位(十进制约 600 多位)的质数。按 NIST SP 800-57 的强度表,2048 位对应约 112 位安全强度,已经逼近"不再建议长期使用"的门槛,3072 位(约 128 位强度)才是 2030 年后的推荐底线。教学例子用小数字是为了让你能拿计算器验证原理,真拿小质数生成密钥毫无安全性可言。

8. PKI 与证书:谁来证明"这把公钥真的是它的"

为什么:非对称加密解决了"钥匙可以公开发布"这件事,却留下一个新漏洞——Alice 拿到一把"Bob 的公钥",怎么确定这真的是 Bob 的,而不是 Eve 冒充 Bob 半路塞给她的一把假公钥?如果 Eve 能成功掉包,后面无论加密还是签名验证,整套体系都在替 Eve 背书。需要一个大家都提前信任的第三方,出来给"这把公钥确实属于这个身份"做担保——这就是 PKI(Public Key Infrastructure,公钥基础设施)。

怎么运作:担保这件事落地成一份数据结构——X.509 证书,格式定义在 RFC 5280 里,本质是"公钥 + 身份信息(比如域名)+ 有效期",整份内容由 CA(Certificate Authority,证书颁发机构)用自己的私钥签一个数字签名(第 6 节的机制原样复用)。验证一份证书,做的正是第 6 节那套签名验证:用 CA 公开的公钥,核对这份证书确实是该 CA 签发、内容没被篡改。

但这又引出同样的问题:怎么信任"CA 的公钥"本身?答案是层层转包,业内叫证书链(certification path)——RFC 5280 把验证规则定义得很严格:链上第 x 份证书的 subject(主体),必须是第 x+1 份证书的 issuer(签发者),一路往上,直到一份自签名的根证书(root certificate)——根证书不再由"更上级"签发,而是作为信任锚点(trust anchor),出厂时就预装进操作系统或浏览器的信任列表里。

普通网站证书很少直接由根 CA 签发——中间通常插着一至多层中间 CA:根 CA 的私钥被视为整条信任链的命脉,平时深锁在离线环境里,只用来签发少数几张中间 CA 证书;日常给成千上万个网站签发证书的活,都交给中间 CA 去干。Let's Encrypt 公开的信任链页面就是这套三层结构在现实里的样子。

实战锚点 · "您的连接不是私密连接"到底在报什么

第 02/03 章那台 iStoreOS 旁路由,管理面板走 HTTPS 访问 https://192.168.1.2 时,浏览器大概率弹出"您的连接不是私密连接"的整页警告。原因不是这条连接没加密——TLS 握手(第 9 节)照常完成,数据在传输路上依然是密文。问题出在这份证书是旁路由自己现签的自签名证书:没有任何链上的 CA 背书,浏览器沿着证书链一路往上找,找不到一个预装在信任库里的根,验证链在半路直接断掉,只能报警交给你自己判断"是否信任这个身份"。这正是 PKI 要解决的问题在真实生活里的样子:加密始终在,但身份担保可能缺失。局域网设备的管理面板选用自签名证书是常见做法(申请一张 CA 签发的证书通常需要一个公网能验证的域名),点"继续前往"本质上是你手动替代了 CA 那份信任担保。

深挖 · 证书曾经是人肉申请,现在是协议自动化

在 Let's Encrypt 和 ACME 协议(Automatic Certificate Management Environment,RFC 8555,2019 年 3 月发布)出现之前,申请一张证书是一整套纯人工流程:生成 CSR(证书签名请求)、粘贴进 CA 的网页表单、用邮件或在网站根目录放一个 challenge 文件证明你控制这个域名、再手动下载安装证书——RFC 8555 原文估计一名网站管理员走完整套流程平均要花 1 到 3 小时,而且完全没有标准化,各家 CA 做法五花八门。ACME 把"证明你控制这个域名"的过程标准化成机器对机器的协议,Let's Encrypt 靠它把证书签发做到了全自动、免费、90 天短有效期强制轮换——今天几乎不再有理由对外公网服务用自签名证书,只是这套自动化没法用在纯内网 IP 这类没有公网可验证域名的场景(比如上面那台 192.168.1.2 的旁路由)。

9. TLS 1.3 握手:把以上全部拼成一次连接

为什么:前面几节的工具——对称加密、非对称加密、哈希、数字签名,外加 PKI 证书体系——单独拿出来都只解决一半问题。真正点开一个 HTTPS 网站,浏览器要在几十毫秒内完成一整套事情:确认这真的是它要访问的服务器(身份认证)、协商出一段只有这一次连接才用的对称密钥(为后续机密性铺路)、还要保证握手过程本身没被动过手脚(完整性)。TLS(Transport Layer Security)就是把这一整套流程标准化的协议,当前版本是 TLS 1.3,定义在 RFC 8446(2018 年 8 月发布)。

怎么运作:RFC 8446 自己列了一份"相对 TLS 1.2 的主要变化"清单,挑几条最关键的:

  • 只保留 AEAD 对称算法(第 3 节提到的 AES-GCM 一类),砍掉了 RC4、CBC 模式配 SHA-1 这些已知有弱点的老算法;
  • 去掉了静态 RSA 和固定 DH 密钥交换,所有密钥交换现在都强制提供前向保密(forward secrecy)——就算服务器的长期私钥有一天被偷,攻击者也解不出去年录下来的历史流量,因为每次握手协商出的会话密钥只用这一次,用完即弃,不直接靠长期私钥本身加密数据;
  • 握手从 2 个 RTT(Round-Trip Time,一次网络往返)砍到 1 个 RTT(外加一个可选的 0-RTT 模式):客户端在第一条 ClientHello 消息里就直接带上密钥交换需要的临时公钥材料(key_share),服务器一次回复就能算出共享密钥,比 TLS 1.2 快整整一轮网络往返;
  • ServerHello 之后的握手消息全部加密,包括服务器证书——TLS 1.2 时代证书是明文传输,谁都能围观是哪家网站、用的什么证书。

把这张图和前面几节对上号:①的 key_share 正是第 4 节非对称/椭圆曲线密钥交换在起作用;②③里的 Certificate + CertificateVerify,正是第 6/8 节的证书链 + 数字签名验证服务器身份;握手全部走完之后的 Application Data,靠的是第 3 节的对称加密高速处理——TLS 1.3 不多不少,正是把本章前面所有工具按照"先用非对称解决密钥分发,再用对称加密处理海量数据"的混合加密思路,组装成了一份可互操作的标准协议。

第 03 章 AdGuard Home 转发去 dns.adguard-dns.com 那个 DoH 上游,走的正是这样一次标准 TLS 握手——只是应用层数据的内容不是网页 HTML,而是一条 DNS 查询。这正是"DoH 让 DNS 查询和普通网页流量长得一模一样"那句话的字面意思:握手过程、证书验证、加密算法,和你打开任何一个 HTTPS 网站完全相同。

避坑 · 0-RTT 快是快,但有代价

TLS 1.3 的 0-RTT 模式(复用上一次连接留下的票据,首个数据包就带业务数据)是 RFC 8446 自己在正文里明确标注的一项"用某些安全属性换速度"的设计——0-RTT 数据缺少前向保密,更麻烦的是它可能被重放(replay):攻击者截获这个早期数据包原样重发一份,服务器可能把它当成一次新的合法请求再处理一遍。RFC 8446 的建议是:0-RTT 只该用在"重复执行也无副作用"的请求上(比如单纯查询),绝不能用来发起转账、下单这类有副作用的操作。是否开启 0-RTT,是在"快"和"防重放"之间做的一次显式权衡,不是免费的午餐。

10. 常见攻击面与避坑

把前九节的工具都用对,不代表万事大吉——密码学历史上大多数真实事故,出在"协议本身没问题,但某个实现细节或使用方式留了缝"。挑几个最常见、最该记住的:

攻击利用的缝隙TLS 1.3 怎么应对
中间人攻击(MITM)攻击者插在 Alice 和 Bob 中间,分别和两边单独建立连接,两头转发并窥视/篡改靠第 8 节的证书链验证服务器身份,让 Eve 没法伪造出一份能通过验证的证书
降级攻击(downgrade)强迫双方"协商"退回到一个已知有漏洞的旧版本协议,再用旧版本的已知漏洞下手握手把版本协商也纳入完整性保护范围,篡改会被检测到
填充预言攻击(padding oracle)老式 CBC 模式对填充字节校验的报错信息被攻击者利用,逐字节猜出明文(经典案例如 POODLE)只允许 AEAD 模式,没有独立的填充校验步骤可被当"预言机"利用
哈希碰撞找到两个不同输入产生相同摘要,伪造一份"签名依然有效"的假文件禁用 SHA-1/MD5,新证书强制要求 SHA-256 起步
避坑 · "有 HTTPS 锁图标"不等于"这网站绝对安全"

TLS 只保证三件事:传输路上的机密性、完整性,以及"证书这一层"的身份认证。它不保证:①服务器本身没被黑(证书再对,后端数据库照样能被脱库);②域名验证型证书(DV,最常见、最便宜的一类)只验证了"申请人确实控制这个域名",完全没有验证运营方的真实身份或经营资质——钓鱼网站一样能合法申请到一张 DV 证书,浏览器地址栏一样显示锁图标;③应用层代码本身没有漏洞(SQL 注入、越权访问这类问题,TLS 完全管不到)。锁图标只回答"这条连接有没有被人偷看/改",从不回答"这个网站本身值不值得信任"。

本章要点
  • 对称加密(AES)一把钥匙锁两道门,快但要先解决密钥怎么安全共享;非对称加密(RSA/ECC)用公私钥对解开这个死结,但慢,现实系统总是把两者混合使用。
  • 哈希函数(SHA-256)把任意内容压成一段不可逆的定长指纹,单靠它能查出"有没有被改",查不出"是谁改的/谁发的"。
  • 数字签名 = 哈希 + 非对称私钥操作的组合拳:私钥签名、公钥验证,一次同时验证完整性和身份——第 09 章 Secure Boot 的 db/dbx 验证、TLS 证书的 CA 签名,底层都是这同一套机制。
  • PKI/证书体系(X.509,RFC 5280)靠一条"根 CA(自签名,预装信任库)→ 中间 CA → 你的证书"的信任链,解决"怎么信任一把陌生的公钥";自签名证书没有这条链背书,浏览器只能报警。
  • TLS 1.3(RFC 8446)把以上所有工具拼成一次 1-RTT 握手:非对称交换临时密钥 → 验证证书链和签名 → 切换到对称加密处理后续所有数据;强制前向保密,0-RTT 用速度换来的是重放风险。
  • 密码学的安全从来不是"绝对破不了",而是"破解代价远超密钥的有效期"——SHA-1 的 SHAttered 碰撞就是活生生的过期案例;有锁图标不等于网站本身可信,TLS 只管传输这一段。
