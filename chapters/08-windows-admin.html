Windows 系统管理与提权

风扇狂转却找不到真凶、软件删了但开机还在自启、共享盘三天两头要求重新登录——这些麻烦的根子都在 Windows 后台那套服务、权限、电源管控机制里,本章把它们逐一拆开,并练一遍怎么揪出真正吃 CPU 的进程。

← 返回首页

把 Windows 想成一栋写字楼:服务是电梯、水泵这类不需要你天天开关的"物业后台";UAC 是每层楼的门禁,默认收起你的门禁卡;powercfg 是给电梯装的限速表;任务管理器则是大堂电表的读数——读数准不准,取决于电表怎么算。四件事合起来,才是"这台电脑后台到底在干什么"的完整答案。

为什么要懂这些

这几件事表面上互不相关,实际上是同一套"谁在后台跑、谁说了算、跑得多快、跑得对不对"的系统管控框架,拆开看是四条独立的线:

  • 服务:像 Corplink 这类软件,开机自己拉起来占后台,想让它"别自动跑",得先知道 Windows 是按什么规则决定谁开机自启的。
  • 提权:很多"删不掉的文件夹""改不了的注册表""被拒绝的操作",本质是权限问题——懂 UAC 才知道该在哪一步"验明正身"。
  • 电源:风扇狂转、笔记本发烫,很多时候操作系统这一层就能直接压住,不必先跟驱动、BIOS 较劲。
  • CPU 诊断:任务管理器那个百分比经常"看着很唬人",不懂它背后的计数器口径,很容易冤枉错的进程。

本章沿用真实场景:一台 Dell 笔记本,风扇狂转、Corplink 开机自己蹦出来占后台——下面每一节都会回到这台机器上。

服务:后台常驻的"物业"

Windows 启动后,桌面上看到的只是冰山一角。真正撑着这栋楼日常运转的,是几十上百个不显示窗口、随系统起停的后台程序——Windows 把它们叫做服务(service)。类比物业:电梯、二次供水泵这类东西,你不会每天亲自去启动——它们要么一直开着,要么有人按了呼叫按钮才启动,要么干脆被物业锁死不让用。这三种情况,恰好对应服务的三种启动类型(startup type)。

三种启动类型,谁说了算

Service Control Manager(SCM,对应进程 services.exe)是这栋楼的"物业总管"。系统启动阶段,SCM 会读取注册表 HKLM\SYSTEM\CurrentControlSet\Services 下每个服务项的 Start 值,决定谁开机自启、谁按需启动、谁被彻底锁死。官方 PowerShell 文档给出的定义很直白:

  • Automatic(自动):系统启动时自动启动;如果一个自动启动的服务依赖另一个手动启动的服务,那个手动服务也会被一并带起来。
  • Manual(手动):只有用户、SCM,或另一个应用显式调用时才会启动。
  • Disabled(已禁用):被禁用,任何用户或程序都无法再启动它。

还有一个变体常被忽略:Automatic(延迟启动)。很多服务(如 Windows Search、Microsoft Edge 更新服务)用这个模式,避开开机瞬间大家一起抢跑、挤爆磁盘和 CPU 的情况,等系统"喘口气"之后再悄悄起来。

实战锚点 · 本会话做过的

关闭 Corplink 开机自启动。最快的路是任务管理器 →「启动应用」标签页,找到 Corplink → 禁用;如果它是以服务方式常驻(而不是登录启动项),就走 services.msc,把 Startup type 从 Automatic 改成 Manual——不建议直接改 Disabled,除非确定以后完全不用。命令行等价写法:

Get-Service Corplink | Set-Service -StartupType Manual

# 或者用最老牌的 sc.exe(注意 start= 后面必须有一个空格,这是 sc 命令出了名的坑)
sc config Corplink start= demand

看门狗:失败后自动恢复

SCM 还兼职当"看门狗"。每个服务都能配置故障恢复(Recovery)动作,官方命令是 sc failure:失败后可以指定「跑一个程序 / 重启服务 / 重启电脑」,第一次、第二次、第三次失败还能配不同的应对。

sc failure Corplink reset= 60 actions= restart/5000
:: 60 秒内没再失败就把失败计数清零;失败后等 5000ms(5 秒)自动重启该服务
原理 · 服务的本质

一个 Windows 服务,本质上是"随内核态启动流程一起被拉起、但自己跑在用户态、并被特别授予了一些普通程序拿不到的权限"的常驻进程。它和你双击打开的普通 App 是同一种"进程"概念,只是生命周期、权限、有没有窗口不一样。这个"用户态常驻进程+特殊权限"的说法,会在 [[11]] 操作系统 一章里,和进程、内核态/用户态、系统调用这些更底层的概念对上号。

避坑

不要看到不认识的服务名字就一律 Disabled。前面表格里带"不要禁用"标记的几个(RpcSs、DcomLaunch、Dhcp、Dnscache、gpsvc、EventLog、Winmgmt 等)是几乎所有其它服务和程序间通信的地基,连锁依赖一断,轻则联网、打印、开始菜单搜索失效,重则系统再也起不来登录界面——这份"红黑名单"来自官方文档,不是经验之谈。

UAC 与提权:钥匙不常挂在腰上

类比:如果你家钥匙一直挂在门口,任何溜进屋里的东西(包括病毒、恶意脚本)都能直接开车、开保险箱。UAC(User Account Control,用户账户控制)做的事,是让"你是管理员"这件事默认收起来——哪怕登录账户在 Administrators 组里,日常操作时手上其实拿的是一把"削了权的钥匙",真要动系统级的东西,得再刷一次卡确认。官方文档的表述是:UAC 通过限制恶意代码以管理员权限静默执行的能力,来降低恶意软件的风险。

两个令牌,一次确认

登录时,如果账户属于管理员组,系统会生成两个访问令牌(access token):一个标准用户令牌(去掉了管理员 SID 和特权),一个完整管理员令牌。桌面外壳 explorer.exe 永远只用标准令牌启动——你双击打开的绝大多数程序,都是从这个"标准用户"进程里长出来的子进程,天生就是普通权限。

当某个程序在自己的清单(manifest)里声明"我需要管理员权限",会触发下面这条链路(对应图 2 下半部分的方框):

  1. 程序清单要求的执行等级,和当前令牌(标准用户令牌)不匹配。
  2. CreateProcess 拒绝这次调用,返回 ERROR_ELEVATION_REQUIRED。
  3. ShellExecute 捕获这个错误,转交给专门处理提权请求的系统服务——Application Information 服务(内部服务名 Appinfo,常被简称 AIS)。
  4. AIS 在安全桌面(secure desktop,屏幕会变暗)上弹出提示,确认后才用早先存好的那份管理员令牌,创建一个全新的、独立的提权进程。

管理员账户看到的是「同意」按钮,标准用户账户看到的则是必须真正输入一次管理员密码的「凭据」提示——这也是"给家人开标准账户、自己留一个管理员账户"这套推荐做法背后的真实机制。

RunAs:不提权整个 Shell,只换一个程序的身份

提权不一定要把整个命令行窗口拉成管理员。runas 可以只让单个程序换个身份跑,更适合"用另一个账户"而不是"提升当前账户"的场景——比如你日常用标准账户,只想临时借一次域管理员身份开一个 MMC 控制台:

runas /user:MYPC\administrator cmd
runas /user:contoso\domainadmin "mmc %windir%\system32\compmgmt.msc"

官方文档特别提醒:通过 runas 换身份运行的程序不会应用该用户的组策略(Group Policy)——这是白纸黑字写明的设计行为,不是 bug,却是不少人踩过的坑。

避坑

远程操作有专门的限制,但这条限制只认本地(非域)账户。如果对方账号是目标机器本地 Administrators 组里的账户(官方文档叫它 SAM 账户,不是域账户),通过 net use \\对方IP\C$ 这类方式远程连接时,你不会以完整管理员身份连进去,没有提权空间,干不了需要管理员权限的操作——这是 LocalAccountTokenFilterPolicy 机制,专门防"本机恶意软件伪装成本地管理员、顺着网络打到别的机器"。换成域账户就不受这条限制:域用户远程登录时,只要在 Administrators 组里,拿到的就是完整、未过滤的管理员令牌,UAC 在这一步不生效(微软文档特别注明,这个行为从 Windows XP 起就是这样,不是新加的限制)。真要用本地账户以完整管理员身份远程管理,得走 Remote Desktop 交互式登录,或者显式把 LocalAccountTokenFilterPolicy 改成 1 放开这条限制。

原理 · 摩擦层,不是权限边界

UAC 的本质是访问令牌机制上的一层"确认摩擦",不是权限边界本身——真正的边界是 SID / ACL 那套访问控制列表。UAC 挡的是"恶意代码悄悄地、静默地"拿到高权限,挡不住"你自己在提示框上点了是"。令牌、SID、内核对象的安全描述符,这些更底层的访问控制概念,[[11]] 操作系统 一章会继续往下讲。

net use / cmdkey:让机器记住"你是谁"

类比:net use 是"接线",cmdkey 是"把身份证提前塞进钱包",这样以后系统连接共享盘时,不用每次翻钱包问你要证件。

net use 把一个盘符(或不带盘符的 UNC 路径)映射到网络共享,可以带用户名密码,也可以用 /persistent:yes 让这次连接在下次开机后自动恢复。cmdkey 直接操作 Windows 凭据管理器(Credential Manager),把"目标(某 IP 或域名)+ 用户名 + 密码"存起来,之后任何走这个目标的连接——不只是 net use,包括资源管理器地址栏手输的 \\ 路径——都会自动套用这份凭据,不再弹密码框。

cmdkey /add:192.168.1.2 /user:pi /pass:你的密码
net use Z: \\192.168.1.2\share /persistent:yes

:: 密码明明没错却报"用户名或密码不正确"?常见原因是缓存了一份旧凭据
:: 先断开所有连接,再去凭据管理器/用 cmdkey 清掉旧条目,才能重新握手
net use * /delete /y
实战锚点 · 本会话做过的

给旁路由(192.168.1.2)上的共享盘配置免密访问,用的就是这套组合拳:先用 cmdkey 把凭据焐热,再 net use 映射盘符,重启电脑后不用重新输密码。[[06]] 文件共享与互传 一章讲了 SMB 协议本身,这里讲的是 Windows 这一侧怎么记住身份、免得每次都重新握手。

powercfg:给处理器装限速表

类比:处理器的 Turbo Boost(睿频加速)像跑车的"弹射起步"——短时间内允许比铭牌标称更高的转速,换来瞬间性能,代价是更烫、更费电、风扇拉到最大声。如果你想要的是安静低温而不是跑分极限,就需要一块"限速表"把弹射起步锁死——这正是 powercfg 里「最大处理器状态」要做的事。

最大处理器状态与 Turbo Boost

Windows 的电源管理叫电源方案(power scheme),每个方案下有一堆子项,处理器相关的子项叫 Processor Power Management(别名 SUB_PROCESSOR)。其中最关键的一个设置是「最大处理器状态」(官方 GUID 别名 PROCTHROTTLEMAX),取值 0–100,代表"最多允许处理器跑到额定基准频率的百分之多少"。

社区里流传很广、但直接建立在这套官方机制上的一个技巧:把这个值从 100 改成 99。100% 时,处理器被允许进入 Turbo Boost 区间(超过额定基准频率);哪怕只降到 99%,系统也会把频率摁在基准附近,不再触发 Turbo——因为"冲上 Turbo"这个动作,本身只在允许"跑满/超过 100% 额定"时才会被触发。

:: 查看当前电源方案里,处理器子项的所有设置
powercfg /query SCHEME_CURRENT SUB_PROCESSOR

:: 插电时:把最大处理器状态限制到 99%(相当于关闭 Turbo Boost)
powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMAX 99
:: 电池供电时同样设置
powercfg /setdcvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMAX 99
:: 让改动对当前方案生效
powercfg /setactive SCHEME_CURRENT
实战锚点 · 本会话做过的

诊断这台 Dell 笔记本风扇狂转,最初怀疑是风扇曲线本身的问题、想装 DellFanCmd 手动控速,结果被 Secure Boot 拦下(详见 [[09]] 固件安全与内核驱动)。绕开驱动层面的折腾,更快见效的一步其实在操作系统这一层:把最大处理器状态压到 99%,直接从源头掐掉 Turbo 触发的功耗尖峰,风扇转速跟着降下来——这是纯软件、不需要驱动签名的路线。

深挖 · 拓展

PPM(Processor Power Management)底下还有一堆没在正文展开的旋钮:核心停靠(core parking)决定"闲的核心"是直接休眠还是保持唤醒以降低响应延迟;最小处理器状态(min processor state)和最大状态相反,是"至少不能低于多少百分比",拉满的话等于强制处理器一直高频空转,笔记本上非常费电;还有 EPP / 能效偏好(energy preference),决定调度是偏性能还是偏省电。这些都在官方 "Processor power management options overview" 文档里,通常由硬件厂商(OEM)出厂时调好,普通用户很少需要碰,但知道它们存在,遇到奇怪的性能或温度问题时能多一条排查线索。

揪出真正吃 CPU 的进程

风扇狂转、电脑发烫,大多数人第一反应是打开任务管理器(Task Manager)看 CPU 那一栏——可这一栏比想象中更容易骗人。

两种计数器,两种"真相"

一份延续了十几年的官方文档说得很清楚(最初编号 KB3200459):从 Windows 8 开始,任务管理器和性能监视器里显示的 CPU 使用率,对应的性能计数器从 % Processor Time(处理器忙碌的时间占比)换成了 % Processor Utility(处理器实际完成的工作量,会把 Turbo Boost 超频这部分也折算进去)。这意味着:如果处理器正顶着 Turbo 跑,折算出来的数字完全可能超过 100%——Windows 只是把它封顶显示成 100%,并不代表"满载"就是它的天花板。

举例:两颗处理器都在 100% 的时间里保持忙碌,一颗被降频到额定 50% 频率,另一颗顶着 Turbo 跑到额定 150% 频率。按老口径(% Processor Time)算,两者看起来都是"100% 忙碌";按新口径(% Processor Utility)算,前者显示 50%,后者会算出 150%(再被封顶显示成 100%)。这也是不少笔记本"任务管理器显示 100%,但看起来并没有干什么"的真实原因之一——一两个核心被 Turbo 冲上高频,折算权重就能把总体数字直接顶满。

性能计数器衡量什么是否受 Turbo 影响会不会超过 100%
% Processor Time处理器忙碌(非 idle)的时间占比不受影响,纯时间片统计不会,单核最高 100%
% Processor Utility处理器实际完成的工作量,按频率折算直接受影响,Turbo 越高折算越大会,可能远超 100%(再被 UI 封顶显示)
深挖 · 拓展

这套算法本身也在变。2025 年前后,Windows 11(24H2 之后的更新)把任务管理器 Processes / Performance / Users 三个页面的口径,统一改回了业界标准的"时间占比"式计量——不再按频率折算,而是老老实实数每个进程实际吃到的 CPU 时间片。原来那套"频率折算"值降级成一个默认隐藏、可手动打开的 CPU Utility 列,专门留给还想看老口径的人。微软官方在 Windows Insider 博客里对这次改动的说法是:「让任务管理器在各页面之间使用一致的标准指标显示 CPU 负载,与业界标准和第三方工具对齐」——博客原文并没有给出逐字的计算公式,下面这条只是这类"时间占比"指标的通用算法示意,帮助理解,不是照抄官方定义:标准 CPU% ≈ (该进程 CPU 时间增量 ÷ (采样间隔时间 × 逻辑处理器数)) × 100%。

怎么真的找到吃 CPU 的进程

比只看总百分比更靠谱的排查顺序:

  1. 任务管理器「详细信息」标签,按 CPU 列排序——这一列走的是不受 Turbo 折算影响的时间占比口径。
  2. 切到「性能」→ CPU,右键选「逻辑处理器」视图,看是所有核心均匀忙碌,还是一两个核心被顶到底——后者更像是单线程任务撞上了 Turbo,而不是真的"整机满载"。
  3. 需要更细粒度(按线程、按调用模块)时,上 Sysinternals 的 Process Explorer,能看到每个线程具体吃了多少 CPU、被谁调用起来的。
避坑

只看任务管理器总览的那根曲线来判断"电脑是不是快撑不住了",在有 Turbo Boost、又有大小核(P-core / E-core)混合调度的现代处理器上已经不太可靠——同一段真实只占 40% 出头的负载,在旧口径下就可能显示成 100%。想真正诊断问题,养成"点进详细信息按列排序 + 看逻辑处理器视图"的习惯,比死盯着总览的那一根曲线有用得多。

本章要点

SCM 按注册表里的 Start 类型(Automatic / Manual / Disabled)决定谁开机自启、谁按需启动、谁被彻底锁死,失败时还能靠 sc failure 配的看门狗自动挽救。UAC 靠"标准令牌常驻、管理员令牌收起来,要用再二次确认"来降低恶意代码静默提权的概率,而不是取代账户 / ACL 那层真正的权限边界。net use / cmdkey 把 SMB 连接和凭据管理串起来,一次配置、长期免密。powercfg 的 PROCTHROTTLEMAX(最大处理器状态)一个数字就能开关 Turbo Boost,是软件层面见效最快的降温、降噪手段。而任务管理器的 CPU 百分比,在 Turbo 与大小核的时代已经不是"所见即所得"——按列排序、看逻辑处理器视图,才是真正定位吃 CPU 进程的办法。这几条线分别通向 [[09]] 固件安全与内核驱动(驱动签名 / Secure Boot 为什么会拦下 DellFanCmd 这类需要内核权限的工具)和 [[11]] 操作系统(进程、内核态 / 用户态、访问控制这些更底层的地基概念)。
