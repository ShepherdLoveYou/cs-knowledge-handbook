为什么需要「运维工程」,不只是「跑起来」

一个服务"能跑起来"和"能稳定运维"是两件事。能跑起来:装上、启动、能访问,今天你在,它就在。稳定运维要多问几个问题:你离开电脑十二小时,它崩了谁知道?硬盘坏了,配置还在不在?想把服务搬到另一台机器,是要从头装一遍,还是复制几个文件就好?改了一处配置,能不能十秒内退回改之前的状态?这些问题的答案,决定了一个自托管的盒子是"玩具"还是"基础设施"。

本章按这几个问题展开:容器(§2-3)解决"怎么打包、怎么搬";卷与网络(§4)解决"数据怎么留住、服务怎么互通";反向代理(§5-6)解决"一堆服务怎么共用一个入口";监控(§7)解决"怎么知道坏没坏";备份(§8)解决"怎么保证数据不会没";CI/CD 与 Git(§9)解决"怎么让改动可控、可回滚"。最后用一张蓝图(§10)把它们和前面章节里你已经搭出来的那台盒子拼在一起。

🛠 实战锚点 · 你已经在"手动运维"了

改 dnsmasq 配置转发给 AdGuard(见〈03 DNS 与去广告〉)、给 Windows 服务掰手腕、调 powercfg 电源计划(见〈08 Windows 系统管理与提权〉)——这些都是运维动作,只是还停留在"打开文件手改、出问题肉眼查"的阶段。本章不是介绍一个新领域,是给你已经在做的事配一套方法论。

容器怎么运作:namespace 管"看见什么",cgroup 管"用多少"

容器常被简化成"轻量级虚拟机",这个说法方便理解但不准确,还会让你对它的隔离强度产生错误的信任。

🧭 原理 · 容器和虚拟机的真实区别

微软官方文档对二者架构差异的定义很清楚:虚拟机在硬件之上跑一个完整的 Hypervisor,每个 VM 里都装着自己独立的操作系统内核;容器则是同一个宿主机内核上跑的一组被隔离的进程,所有容器共享宿主机唯一的那个内核。共享内核带来的直接好处是容器启动是毫秒级的(不用像 VM 那样启动一整个操作系统),镜像体积也小得多;代价是隔离强度理论上弱于 VM——内核层面的漏洞可能牵连到所有容器。

让"共享一个内核却还感觉彼此独立"成立的,是两个 Linux 内核原语:namespace 和 cgroup。它们分工非常明确,记住这一句就抓住了容器的本质:namespace 决定一个进程能看见什么,cgroup 决定它能用多少。

namespace:决定"一个进程能看见什么"

Linux 内核文档把 namespace 定义为对全局系统资源的一层包装,让一组进程以为自己独享这份资源,而系统里实际上可能同时存在好几份、分别属于不同的进程组。通俗说:namespace 给每个容器发一副"眼罩",它只能看到分配给自己的那一份东西,看不到宿主机上其他容器和进程。

namespace 类型隔离的资源容器里的体验
pid进程 ID 空间容器里第一个进程的 PID 是 1,看不到宿主机或其他容器的进程
net网络接口 / 路由表 / 端口容器有自己的 eth0、自己的 IP、自己的一整套端口空间
mnt文件系统挂载点容器的 / 只是镜像内容,看不到宿主机真实目录树
uts主机名 / 域名容器可以有自己的 hostname,不影响宿主机
ipc进程间通信(信号量 / 消息队列)容器间默认不能用 System V IPC 直接通信
cgroup容器自己在 cgroup 目录树里看到的根路径容器里看到的 cgroup 路径以 / 为根,看不到宿主机上真实的完整路径和其他容器的配置
user用户 / 组 ID容器里的 root(UID 0)可以映射成宿主机上一个无特权 UID

Docker 默认为每个容器创建 mnt、uts、ipc、pid、net 这 5 种 namespace 是恒定的;cgroup namespace 是否默认创建则取决于宿主机的 cgroup 版本——Docker 官方文档对 --cgroupns 的说明是:未显式指定时跟随 dockerd 的 default-cgroupns-mode,在 cgroup v1 宿主机上默认值是 host(容器与宿主机共享同一个 cgroup namespace),在 cgroup v2 宿主机上默认值是 private(每个容器再拿到一个独立的 cgroup namespace)。也就是说,在当下已普遍升级到 cgroup v2 的宿主机上(见下节),Docker 默认其实一共创建 6 种 namespace,而不是 5 种。user namespace 不受这个影响,任何情况下都默认不开启,需要显式配置(如 --userns-remap)才会做二次隔离——它才是真正唯一"默认关闭、必须自己开"的一种。

延伸:Linux 目前支持的全部 namespace 种类

除了上表 7 种,Linux 内核文档里还记录了 time namespace(允许容器拥有和宿主机不同的系统启动时间 / 单调时钟偏移,常用于迁移热备场景)。八种 namespace 共同的设计哲学是同一句话:把某个全局资源"包一层",让容器组看到的是自己专属的一份。

cgroup:决定"一个进程能用多少"

namespace 解决了"看不看得见",但没解决"用多少"——如果没有限制,一个容器里失控的进程一样能把宿主机的 CPU 或内存吃满,拖垮同一台机器上的其他容器。这是 cgroup(control group)的工作:Linux 内核用它限制、统计、隔离一组进程的 CPU、内存、磁盘 I/O、网络等资源用量。

# 手动演示 cgroup 在做什么(Docker 平时会替你自动完成这几步)
# 下面是 cgroup v2(统一层级)的路径——当前主流发行版的默认状态,见下方避坑说明
mkdir -p /sys/fs/cgroup/myapp
echo 500000000 > /sys/fs/cgroup/myapp/memory.max        # 内存上限约 500MB
echo 12345 > /sys/fs/cgroup/myapp/cgroup.procs           # 12345 换成实际要限制的进程 PID
⚠️ 避坑 · cgroup v1 与 v2 的路径、文件名都不一样

上面这份是 cgroup v2(统一层级,unified hierarchy)的写法:没有独立的 memory/ 子目录,文件名以 .max 结尾。Ubuntu 21.10+、Debian 11+、Fedora 31+、RHEL 9+ 等主流发行版自 2021-2022 年前后起已默认启用 cgroup v2,Docker 20.10+ 在这些宿主机上也默认走 v2。老资料里常见的是 cgroup v1 的写法——每种资源单独一棵目录树、文件名也不同,例如同样限制内存要写成 mkdir -p /sys/fs/cgroup/memory/myapp 配 memory.limit_in_bytes。想确认自己机器用的是哪一版,看 /sys/fs/cgroup/cgroup.controllers 这个文件存不存在——存在就是 v2。

🔍 深挖 · Windows 上的 docker run 其实是……

namespace 和 cgroup 都是 Linux 内核的能力,Windows 的 NT 内核并没有这两样东西。所以 Docker Desktop 在 Windows 上默认走 WSL 2(Windows Subsystem for Linux 2)——微软官方文档在"Full Linux kernel"一节里写得很直接:"The Linux kernel in WSL 2 is built by Microsoft from the latest stable branch, based on the source available at kernel.org."(WSL 2 里的 Linux 内核由微软基于 kernel.org 上的最新稳定分支自行构建)——偷偷养一个真正的 Linux 内核,你在 PowerShell 里敲的 docker run,容器实际养在这个 Linux 内核里,只是外壳做得让你感觉不到。这也是为什么 Docker Desktop 分"Linux containers"和"Windows containers"两种模式:后者用的是 Windows 自己的隔离机制(Job Object),和本节讲的 namespace/cgroup 是完全不同的两套东西。内核态 / 用户态和这些隔离机制更底层的关系,见〈11 操作系统〉。

镜像与层:为什么容器秒起,镜像还能"共享"

一个 Docker 镜像不是一个整体文件,而是若干只读"层"(layer)叠在一起;从镜像启动一个容器时,Docker 会在最上面再加一层可写的"容器层"。官方文档把这套设计总结为写时复制(copy-on-write,CoW)策略:容器里的进程第一次要修改一个属于只读层的文件时,存储驱动不会去动那个只读层,而是先把这个文件整份复制到可写层,再在副本上修改。镜像本体永远不会被写坏,这也是为什么同一个镜像能被无数容器同时启动而互不干扰——大家共享同一份只读层,各自的改动只发生在自己的可写层里。

Linux 上最常用的 overlay2 存储驱动把这个模型落到磁盘上:镜像的只读层叫 lowerdir,容器自己的可写层叫 upperdir,OverlayFS 内核模块把它们叠成一个叫 merged 的统一视图交给容器里的进程——进程完全感觉不到自己面对的是好几层叠出来的假象,以为这就是一个普通、完整的文件系统。官方文档还指出这套设计"促成更小的镜像"(sharing promotes smaller images):如果两个镜像都基于同一个基础镜像,Docker 在磁盘上只存一份那些公共层,后续镜像只需要多存自己独有的层。

$ docker image inspect --format "{{json .RootFS.Layers}}" python:3.12-slim
["sha256:72e830a4dff5f0d5225cdc0a320e85ab1ce06ea5673acfe8d83a7645cbd0e9cf",
 "sha256:07b4a9068b6af337e8b8f1f1dae3dd14185b2c0003a9a1f0a6fd2587495b204a"]

(你本地跑出来的哈希值会不一样——这是正常的,python:3.12-slim 这个 tag 会随镜像重新构建而重新指向新的层;这里要看的是"只有两层"这个结构,不是具体数值。)

⚠️ 避坑 · 容器可写层没了就真没了

这是自托管新手最常摔的一跤:把数据库、配置、上传的文件直接写在容器内部(可写层),测试很顺利,直到你 docker rm 或重建这个容器——可写层跟着容器一起消失,里面的数据没有第二份拷贝,直接归零。任何你想活过 docker rm -f、活过重建、活过换机器的数据,必须放进下一节讲的卷,而不是留在容器可写层里。

🔍 深挖 · 每一层的"名字"都是它内容的哈希

上面 docker image inspect 打印出的是一串 sha256:… 值——每一层的标识就是它内容的哈希。内容变了,哈希跟着变;Docker 靠比较哈希就知道两层是不是完全相同的内容,判断能不能共享磁盘空间,不需要逐字节比较文件。这和〈13 数据结构与算法〉里哈希表的寻址思路是同一件事——按内容算出的哈希直接当"地址"用,业内称为内容寻址存储(content-addressable storage)。§9 讲 Git 内部结构时还会再碰到同一套思路。

卷与网络:数据怎么活下来,容器怎么互相说话

卷:让数据活过容器的生命周期

官方文档对卷(volume)的定义是:由 Docker 创建和管理的持久化数据存储,专门保存容器产生、需要长期保留的数据。它和另一种常见方式——绑定挂载(bind mount,直接把宿主机某个目录路径塞进容器)最大的区别在于:绑定挂载依赖宿主机那个目录本来就存在、路径结构不能变;卷则完全由 Docker 管理存放位置,你不需要关心它具体存在磁盘哪个角落。

场景推荐方式原因
直接编辑宿主机上的配置文件,让容器读取bind mount改宿主机文件立刻生效,路径自己掌控
数据库数据、容器自己生成的运行数据volumeDocker 管理生命周期,不依赖宿主机目录结构,备份 / 迁移更规整
开发时把源代码挂进容器实时预览bind mount编辑器改代码,容器里立刻同步看到

网络:容器怎么找到对方

容器默认自带网络隔离(net namespace),但完全孤立就没法协作了。Docker 的解法是创建一个软件网桥(bridge)——默认桥接网络就叫 bridge,新建容器不指定网络时自动挂上去;但更推荐的做法是自己建一个用户自定义桥接网络,因为在这种网络里,Docker 内置的 DNS 服务会让容器之间可以直接用容器名(或 compose 里的服务名)互相访问,不需要硬编码 IP——下一节的实例会直接用到这一点。容器默认只能被同一网络里的其他容器访问;要让宿主机之外的世界连进来,需要显式发布端口(-p 宿主机端口:容器端口),Docker 才会把宿主机对应端口的流量转发进容器。

🛠 实战锚点 · 又是同一套"私网 + 网关"逻辑

旁路由(见〈02 软路由与旁路由〉)给局域网设备发的是 192.168.1.0/24 网段的地址,靠 NAT 出公网;Docker 的 bridge 网络给容器发的是它自己那个私有网段(常见 172.17.0.0/16)的地址,靠端口发布决定谁能从外面连进来。同一套"私网 + 网关 + 按需开放"的思路,只是这次的"局域网"被压缩到了一台电脑内部——概念对照见〈10 计算机网络体系〉。

反向代理:一个入口,任意后端

Cloudflare 官方的定义很干脆:反向代理是一台立在一个或多个后端服务器前面、拦截客户端请求的服务器——客户端只知道、只连接反向代理,完全不知道真正处理请求的服务器是谁、在哪。这和更常见的正向代理刚好镜像对称:正向代理立在客户端前面,代表客户端向外发请求;反向代理立在服务器前面,代表服务器接收请求。当你在一台机器上塞了不止一个服务——管理页、静态站、别的什么 web 应用——反向代理能把它们全部收敛到 80/443 两个端口,按域名或路径分发到正确的后端,不需要给每个服务单独开一个奇怪的端口号让别人记。

🧭 原理 · 你已经搭过一条逻辑一模一样的转发链

回到〈03 DNS 与去广告〉那条链路:客户端只认 dnsmasq 的 53 端口,dnsmasq 把没有命中内网主机名的查询转发给背后监听 5335 端口的 AdGuard Home 去处理——查询方完全不需要知道、也不关心背后真正干活的是谁。这正是反向代理"统一入口,后端可以随时更换"的核心逻辑,只是那条链发生在 DNS 协议层,这一节说的反向代理发生在 HTTP/HTTPS 层,原理完全一致。

本章示例用 Caddy,因为它有一个特别适合自托管的官方卖点——"Caddy 是第一个默认就自动开启 HTTPS 的 web 服务器":只要配置里写清楚域名,Caddy 会自动申请、续期 TLS 证书,不需要手动跑 certbot 或记得证书什么时候过期。

# Caddyfile —— 一个完整、能跑的反向代理配置
adguard.example.com {
    reverse_proxy 127.0.0.1:3000
}

这几行就是完整配置:凡是发到 adguard.example.com 的请求,Caddy 自动拿到证书、终结 TLS,再把请求转发给本机 3000 端口。证书怎么签发、TLS 握手具体在谈判什么,留到〈15 密码学与网络安全〉细讲。

实例:把 AdGuard Home 装进容器,配 Caddy 反代出 HTTPS

把前面几节的概念拼成一个能真正跑起来的例子——不是要你现在就去换掉旁路由上跑得好好的那份 AdGuard Home,而是理解"容器 + 卷 + 网络 + 反向代理"这套组合具体怎么落地成几个文件。

# docker-compose.yml
services:
  adguardhome:
    image: adguard/adguardhome
    restart: unless-stopped
    volumes:
      - ./adguard/work:/opt/adguardhome/work
      - ./adguard/conf:/opt/adguardhome/conf
    ports:
      - "53:53/tcp"
      - "53:53/udp"
      - "3000:3000/tcp"   # 仅首次安装向导用
    networks: [lan]

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
    networks: [lan]

networks:
  lan:

volumes:
  caddy_data:
# Caddyfile
adguard.example.com {
    reverse_proxy adguardhome:3000
}

注意 Caddyfile 里写的是 adguardhome:3000,不是某个 IP——因为 caddy 和 adguardhome 两个容器被 compose 自动放进同一个用户自定义网络 lan,Docker 内置 DNS 让 caddy 直接用服务名 adguardhome 就能解析到对方的容器 IP,不需要硬编码、也不怕 IP 重启后变化(呼应上一节§4的网络机制)。

⚠️ 避坑 · 反向代理搬不动 DNS 协议

Caddyfile 里的 reverse_proxy 指令面向的是 HTTP(S) 流量,AdGuard Home 真正对外提供 DNS 服务的 53 端口(UDP 为主、TCP 兜底大响应)不需要、也不能塞给 Caddy 转——上面的 compose 文件里 53 端口是直接从 adguardhome 容器发布到宿主机的,和走 Caddy 的管理页是两条完全独立的路径。反向代理统一的是"网页 / API 这一类 HTTP 流量",不是所有网络协议。

🛠 实战锚点 · 端口 3000 只是"新手引导"

AdGuard Home 官方镜像文档专门把 3000 标成"初次安装向导"端口——第一次启动时用它走一遍设置流程(选管理员账号、选正式监听端口),设置完成后 AdGuard Home 会切到向导里选定的正式端口。上面的 Caddyfile 为了示例简单统一写 3000;真实部署时把 reverse_proxy 后面的端口换成向导里最终确定的那个即可。

监控与可观测性:在故障影响到人之前发现它

行业里把可观测性(observability)拆成三大支柱:指标(metrics)、日志(logs)、追踪(traces)。三者解决的问题不同,配合起来才完整——指标负责第一时间告诉你"有问题",追踪负责展示请求走过的路径,日志负责提供定位问题所需要的具体上下文。

支柱是什么回答的问题例子
指标 metrics随时间变化的数字时间序列现在状态怎么样?有没有异常?CPU 占用 92%、请求延迟 p99 = 800ms
日志 logs按时间顺序记录发生的具体事件具体发生了什么、报了什么错?"容器 adguardhome 因内存超限被杀"

🛠 实战锚点 · Windows 自带的"本地版"可观测性

〈08 Windows 系统管理与提权〉里用过的任务管理器实时 CPU/内存图表,就是最朴素的"指标";事件查看器(Event Viewer)按时间顺序记录的系统 / 应用事件,就是最朴素的"日志"。它们唯一缺的是:集中化(多台机器只能一台台点开看)、历史存档(重启就可能被冲掉)、自动告警(不会在你不看屏幕时主动喊你)——这正是 Prometheus(采集 + 存储指标)、Grafana(可视化 + 告警)这类自托管可观测性工具要补上的。

⚠️ 避坑 · 告警太多 = 没有告警

如果每一次 CPU 抖动、每一次容器重启都发一条告警,人很快会学会"已读不回";等真正的故障发生,那条关键告警混在几十条噪音里被一起划掉。告警要少而准,只对"需要人立刻处理"的情况响,这比接入更多监控指标本身更重要。

备份:3-2-1 法则

3-2-1 法则是数据备份行业最广泛引用的经验法则,常被追溯到摄影师 Peter Krogh 在《The DAM Book: Digital Asset Management for Photographers》一书中的表述:保留 3 份数据拷贝(1 份原始 + 2 份备份),存在 2 种不同类型的存储介质上,其中至少 1 份放在异地。"2 种介质"防的是同一类介质集体失效——比如同批买的移动硬盘一起进入寿命末期,或只依赖一家云盘账号被盗;"1 份异地"防的是整个现场一起出事——失火、被盗、勒索软件加密了当前网络能碰到的所有东西。两个风险的性质完全不同,缺一个防护都不完整。

拿这本手册的产出练手:① 原始文件放在 Windows 笔记本本地磁盘;② 第二份拷贝放进局域网里一块外接硬盘或 NAS(不同介质);③ 第三份同步到云端网盘或代码仓库(异地)——三份、两种介质、一份不在本地,就是完整的 3-2-1。

🔍 深挖 · 勒索软件时代的 3-2-1-1-0

Veeam 等备份厂商近年在经典 3-2-1 后面又加了两位:多一个"1"要求至少 1 份拷贝是不可变或离线隔离的(immutable / air-gapped)——防的是勒索软件连你的备份服务器一起加密;多一个"0"要求定期做恢复演练、验证 0 个错误——一份从没试过恢复的备份,你并不真的知道它能不能用。

⚠️ 避坑 · 没测试过恢复的备份,等于没有备份

很多人的"备份"做到"按时把文件复制走"就停了,从没实际试过用它把系统恢复回来。压缩包损坏、云同步半途中断、脚本悄悄从某天起就没再跑——这些故障只有在你真正需要恢复的那一刻才会暴露,而那时候往往已经太晚。定期挑一份备份,真的拿它做一次完整恢复演练。

CI/CD 与 Git:让每一次改动可控、可回滚

Git 的核心思想是把每一次改动存成一个不可变的快照(commit),每个 commit 指向它的上一个 commit,连成一条(或分叉成多条,即分支 branch)历史链。这条链不仅是"版本历史",也是接下来整条 CI/CD 流水线的触发起点——一次 git push,理想情况下应该能自动导向一次安全的线上更新,而不需要手动 SSH 上服务器改文件。

🔍 深挖 · Git 内部是一棵哈希寻址的树

Git 存储的每个对象(commit / 目录树 tree / 文件内容 blob)都用它内容的 SHA 哈希作为唯一标识,对象之间用哈希互相指向,整体组成一个有向无环图(DAG)——这和 §3 提到的镜像层哈希是同一套"内容寻址"思路,也是〈13 数据结构与算法〉里哈希表和树结构在真实工程系统里最直接的应用之一。

CI(持续集成,Continuous Integration):每次有人往共享仓库推代码,自动拉取、构建、跑测试,尽早发现"这段代码和别人那段代码合不到一起"的问题。CD 这个字母通常有两种含义:持续交付(Continuous Delivery)是自动走完构建和测试,但最后一步"推上生产环境"留给人工点一下确认;持续部署(Continuous Deployment)是连最后这一步也自动化,测试一过直接上线,没有人工卡点。GitHub 官方把 GitHub Actions 定义为构建在仓库上的持续集成 / 持续交付平台:一个 YAML 文件描述"什么事件触发"(比如 push 到 main 分支)和"触发后按顺序执行哪些步骤"。

⚠️ 避坑 · 说"CI/CD"时,"CD"不一定是全自动上线

这是最常被混用的一对术语——很多人说"我们做了持续部署",实际做的是持续交付(测试过了但仍要人点一下才上线)。混着说不影响自己用,但和别人对接协作时最好先确认清楚:"合并到主分支"和"用户已经用上新版本"中间,到底还隔不隔着一次人工确认。

把整条流水线摊开,自托管场景下典型的样子是这样——注意第 3、5 步正好呼应本章前半讲的镜像与容器:

  1. 提交并推送:git push 触发流水线。
  2. CI 跑测试:拉取代码,自动跑单元测试 / 集成测试。
  3. 构建镜像:测试全部通过后,构建一个新的容器镜像(见 §3〈镜像与层〉)。
  4. 推送镜像:把新镜像推送到镜像仓库(registry)。
  5. CD 上线:自动或经人工确认后,在目标机器上把旧容器换成跑新镜像的容器——本质上就是 §6 那个 compose 文件里的 image 版本变了,重新 docker compose up -d。
延伸:除了 GitHub Actions,常见的 CI/CD 工具还有哪些

GitLab CI/CD(和代码托管深度绑定)、Jenkins(自托管、插件生态最老最全)、CircleCI、Drone CI(轻量、原生面向容器)都是同一套"事件触发 → 按步骤自动执行"思路的不同实现,选择通常取决于代码托管在哪、要不要自己维护执行环境。

🛠 实战锚点 · 对比〈08〉里的手动模式

〈08 Windows 系统管理与提权〉里"改完文件、手动重启服务"的模式,本质上就是没有 CI/CD 时唯一的部署方式——好处是简单直接,坏处是没有测试关卡(改错了要等它炸了才知道)、没有历史记录(想退回上一个能用的版本,得自己记得上一次改了什么)。CI/CD 把这两样短板都补上了。

📌 本章要点

容器不是轻量 VM——它是共享宿主机同一个内核、靠 namespace(决定看得见什么)+ cgroup(决定能用多少)做隔离的进程组;Windows 上的 Docker Desktop 实际靠 WSL2 养一个真 Linux 内核来提供这两样东西。镜像是叠起来的只读层,容器在最上面加一层可写层,写时复制(CoW)保证镜像本体永远不被写坏、还能被多个容器共享;可写层随容器一起消失,任何要保留的数据必须放进卷。容器网络默认靠用户自定义 bridge + Docker 内置 DNS 用服务名互相找到对方,发布端口才能被外部访问——和旁路由的私网 + NAT 是同一套思路的缩小版。反向代理(如 Caddy)把多个服务收敛成一个入口、统一签发续期 HTTPS 证书,但只搬得动 HTTP(S) 流量,DNS 这类协议仍需直接发布端口。可观测性三支柱——指标告警、日志定位、追踪溯源——配合起来才知道"坏没坏"和"坏在哪"。3-2-1 备份法则(3 份拷贝、2 种介质、1 份异地)是应对数据丢失最基本的纪律,且必须定期演练恢复。CI/CD 把 git push 到线上更新之间的"测试关卡"和"变更记录"自动化,持续交付和持续部署的区别在于最后一步要不要人工点头。这六件事拼在一起,把手册前面章节里那台靠你手动运维的盒子,升级成一套有工程方法支撑、能自己扛住常见故障的自托管基础设施。
