为什么需要 DNS —— 机器认地址,人认名字

你的电脑、手机、路由器之间,靠的是一串数字地址(IP,如 93.184.x.x 这样的四段数字,或更长的 IPv6)互相找到对方。但人脑记不住数字——就像你不会去背朋友的手机号码,而是在通讯录里存一个名字。DNS(Domain Name System,域名系统)做的就是这件事:把人能记住的名字(example.com)翻译成机器能用的数字地址。

最早的互联网(那时还叫 ARPANET)确实是「一个通讯录」——每台主机在本地维护一份 HOSTS.TXT 文件,人工汇总、定期从中心节点下载更新。随着联网主机数量增长,这种「单一大本子,手工同步」的模式很快就撑不住了:更新有延迟,单点还会成为全网瓶颈。RFC 1034 和 RFC 1035(1987 年发布,DNS 的奠基文档)给出的解法不是造一本更大的本子,而是把这本通讯录拆开,分层分责——没有人独自拥有全部答案,但顺着层级问下去,总能问到知道答案的那一个。这就引出了下一节的分层世界。

域名的分层世界 —— 根、顶级域、权威服务器

域名要从右往左读才是它真正的层级顺序。以 www.example.com 为例:

层级本例中的值负责的服务器职责
根(root).(通常省略不写)根服务器不知道 example.com 具体在哪,但知道该去问哪个 TLD 服务器
顶级域(TLD).comTLD 服务器不知道 example.com 的 IP,但知道它的权威服务器是谁
二级域example权威名称服务器持有 example.com 这个「区」(zone)里全部记录的最终答案
主机名www—区内的一条具体记录(A / AAAA / CNAME …)
🎓 原理 · RFC 1034 的角色定义

RFC 1034 §4-5 把 DNS 参与者严格分成几种角色:递归解析器(recursive resolver,代替你跑腿问一圈)、根服务器、TLD 服务器、权威名称服务器(authoritative name server,对某个「区」拥有最终解释权)。这四个术语在 408 统考的计算机网络科目里对应「应用层协议」考点,DNS 是除 HTTP/SMTP 外最常考的应用层协议之一——因为它优雅地演示了「分布式层级查找」这个通用设计模式(和文件系统目录树、路由聚合是同一种思路)。

🔎 深挖 · 为什么根服务器恰好是 13 个

互联网上被写进「根提示文件」(root hints)的根服务器名字只有 13 个逻辑地址(a.root-servers.net 到 m.root-servers.net)。这不是拍脑袋定的数字,而是历史上 DNS 报文必须塞进一个 512 字节的 UDP 包这条硬约束推出来的结果——13 条 NS 记录 + 对应的 A 记录胶水记录(glue record),已经接近 512 字节能装下的上限,再往上加就容易溢出触发 TCP 重传,拖慢当年羸弱的网络。(按字节精算:12 字节 header + 5 字节 question + 13×31 字节 NS 记录 + 13×16 字节 glue A 记录 ≈ 436 字节,离 512 字节还留了约 1-2 台服务器的余量才会真正超限——13 是历史上定下来的、留有安全边际的数字,并非卡到临界值的精确数学上限。)这个数字后来就成了事实标准一直保留至今。不过「13 个名字」≠「13 台机器」:借助 anycast(任播,多台机器共享同一个 IP,由路由就近调度请求),截至 2025 年底,这 13 个逻辑地址背后的物理服务器实例已经超过 1900 台,分布在全球各地。现代 DNS 通过 EDNS(0)(RFC 6891)把这个包大小上限从 512 字节抬到了 4096 字节甚至更高,但「13」这个历史遗留数字已经很难再改——全球有太多老旧设备的根提示文件还硬编码着这份列表。

递归查询 vs 迭代查询 —— 谁在替你跑腿

知道了「谁负责什么」,接下来的问题是:问一圈这件苦差事,谁来干?DNS 用两种查询方式回答这个问题:

  • 递归查询(recursive query):你的电脑只问一次,把「问一圈」这件事完全甩给递归解析器——不管它要跑多少趟,你只要一个最终答案。
  • 迭代查询(iterative query):递归解析器每问一台服务器,对方要么给出最终答案,要么回一句「我不知道,但你可以去问它」(这叫转介,referral)——解析器拿着这个线索,自己一步步问下去,而不是坐等对方替它跑腿。

关键在于:你的电脑和递归解析器之间是递归关系,递归解析器和根/TLD/权威服务器之间却是迭代关系——根服务器和 TLD 服务器从不会替你「继续问下去」,它们只负责转介。下图画出这条完整的路径:

缓存与 TTL —— 为什么不用每次都跑一遍

图 1 那趟「4 跳迭代查询」如果每次访问网页都跑一遍,延迟会很痛苦。解决办法是缓存:权威服务器给出的每条记录都带一个 TTL(Time To Live,存活时间,单位秒),递归解析器会把「问到的答案」连同 TTL 存进本地内存。TTL 到期之前,同一个域名的后续查询直接用缓存回答,不必再走一遍图 1 的全程。这也是为什么改了域名解析后「有的地方生效快、有的地方生效慢」——每一层缓存都在按自己记住的 TTL 倒计时。

展开:DNS 报文长什么样?

一个 DNS 报文(RFC 1035 §4.1)由 5 部分组成:12 字节的 Header(含 QR 位区分请求/响应、Opcode、RD/RA 表示是否要求 / 支持递归、rcode 错误码等标志位)、Question(问的是什么名字、什么记录类型)、Answer(答案记录)、Authority(权威区的 NS 记录)、Additional(附加的胶水记录,比如 NS 记录对应的 IP)。传统 UDP DNS 报文上限是 512 字节(前面深挖框提到的历史包袱),EDNS(0)(RFC 6891)通过在报文里加一条伪记录(pseudo-RR)把这个上限协商到 4096 字节甚至更大,才能塞下 DNSSEC 签名这类更大的数据。

实战 —— dnsmasq 转发给 AdGuard Home 做广告过滤

理论讲完,回到本手册第 02 章搭的那台 iStoreOS 旁路由(192.168.1.2)。它身上同时跑着两个和 DNS 相关的软件,各管一段:

  • dnsmasq:官方文档把它定义为「DNS query forwarder」——一个轻量级转发器 + 缓存,它自己不会像根/TLD/权威那样从零做递归解析,而是把查询转发给上游一个能做完整递归的 DNS 服务。它最大的价值是和 DHCP 深度绑定:给内网设备分配 IP 的同时记住每台设备的主机名,于是局域网内可以直接用设备名互相访问。
  • AdGuard Home:官方定义是一个把追踪 / 广告域名解析请求「重定向到一个黑洞(sinkhole)」的 DNS 服务,本质上是一层过滤代理——规则命中就不让你连上广告服务器,规则没命中就继续把查询转发给它自己配置的上游。

问题来了:两者都想监听 53 端口(DNS 的标准端口),但一台机器上一个端口只能被一个进程占用。这不是理论推演——AdGuard Home 官方 issue 跟踪器里明确记录过这个真实冲突:安装时报错「port 53 is occupied by your local dnsmasq instance」,解法只有两条:要么关掉 dnsmasq 的 DNS 功能只留 DHCP,要么让 AdGuard Home 换一个非标准端口监听。本会话选的是后者——接力而不是二选一,因为 dnsmasq 的 DHCP+主机名解析仍然要留着。

🛠 实战锚点 · 本会话真实配置

dnsmasq 端只需要两行(OpenWrt/iStoreOS 上等效地写进 /etc/dnsmasq.conf 或 LuCI 的 DHCP/DNS 转发设置里):

no-resolv
server=127.0.0.1#5335

dnsmasq 官方手册对 --server 选项的原文定义是:「Specify upstream servers directly. A non-standard port may be specified as part of the IP address using a # character.」——#5335 就是告诉 dnsmasq「把没有更精确匹配规则的查询,转发到本机 5335 端口」,也就是 AdGuard Home 的 DNS 监听端口(它的管理面板是另一个端口,常见默认是 3000,二者不要混淆)。选一个像 5335 这样的非标准端口,正是为了绕开前面提到的「两个进程抢 53」的真实冲突。

跨设备互传相关的局域网协议(SMB、AirDrop 等价物)见 第 06 章;DNS 在整条协议栈里处于哪一层、和 TCP/UDP/HTTP 的关系,见 第 10 章 · 计算机网络体系。

加密 DNS —— DoH 与 DoT 补上明文的洞

图 2 里从 AdGuard Home 到公网上游那一段,画的是加密的连接,这不是随手加的细节。传统 DNS 走明文 UDP/TCP 53 端口——链路上任何一个中间人(公共 WiFi 热点、运营商、任何能看到你流量的设备)都能看到你查询了哪个域名,甚至能伪造一个假答案把你导向钓鱼网站。要命的是,就算你之后访问的是 HTTPS 网站,DNS 查询本身发生在 HTTPS 握手之前,域名早就在这一步暴露了。DoH 和 DoT 就是为了补上这个洞:

方案端口底层加密标准特点
明文 DNS53无RFC 1035(1987)默认方式,链路上任何人可见、可篡改
DoT · DNS over TLS853(专用)TLSRFC 7858(2016)独立端口,便于企业按端口识别与管控;但端口本身容易被防火墙整体封锁
DoH · DNS over HTTPS443(与网页共用)TLS(HTTP/2 或 HTTP/3)RFC 8484(2018)和普通网页 HTTPS 流量混在一起,几乎没法单独拦截;但把解析请求集中给了少数几家运营 DoH 的服务商
DoQ · DNS over QUIC853(默认)QUIC 内的 TLS 1.3RFC 9250(2022)基于 UDP 的 QUIC,每条查询独立成流,消除队头阻塞;浏览器/系统支持还在铺开中

AdGuard Home 的上游配置里,这几种写法都能直接用前缀区分(udp:// / tcp:// / tls:// / https://…/dns-query / quic://),这也是它比裸 dnsmasq 更适合放在过滤链路末端的原因之一——上游加密这一段几乎是「填地址」级别的配置成本。

🎓 原理 · 加密 ≠ 验真,DoH/DNSSEC 是两回事

RFC 8484 §9 明确写道:DoH 提供的是传输层的机密性(TLS 保护你和服务器之间不被偷看/篡改),但不提供 DNSSEC 那种「响应内容真实性」的保证——DoH 只保证「没人在半路改你和 AdGuard 之间的这段悄悄话」,不保证「AdGuard 上游给的答案本身没有被更早一环的人下毒」。DNSSEC(用公钥签名给每条记录背书)解决的是后一个问题,二者互补而非互斥,可以同时开启。这与第 15 章要讲的「加密 vs 签名」是同一组概念在不同协议里的复用。

🔎 深挖 · DoH 让网络管理员「失明」的争议

DoH 把 DNS 流量伪装成普通 HTTPS 网页流量,这对普通用户是隐私利好,却让企业网络管理员没法再靠「盯着 53/853 端口」的老办法做内容审计或安全过滤——除非连 443 一起封,但那会连所有 HTTPS 网站一起封掉。这也是为什么很多讨论里 DoT 被认为更适合企业内网(可按 853 端口精细管控),DoH 更适合终端用户设备(浏览器原生支持、难以被单独针对)。这组张力本身就是「加密」与「可管理性」互相拉扯的一个经典案例。

避坑 —— 两个真实会漏掉的洞

即使上面这条链路配置得再干净,仍有两个环节可能在你毫无察觉的情况下绕开它。

⚠️ 避坑 · IPv6 DNS 泄漏

假设你已经把图 2 那条链路配得很干净:dnsmasq → AdGuard → 加密上游,IPv4 查询滴水不漏。但如果你的 ISP 或路由器仍然通过 IPv6 的 Router Advertisement(路由通告,里面可以带 RDNSS 选项直接下发 IPv6 DNS 服务器地址)在给内网设备指派 DNS,支持双栈的客户端完全可能绕开你精心搭的 AdGuard,直接用 IPv6 去问 ISP 的默认 DNS——过滤失效,还可能暴露真实的查询记录。IPv6 地址本身通过 AAAA 记录解析(和 IPv4 用的 A 记录并列存在,同一个域名可以同时有 A 和 AAAA 两条记录)。排查方法很直接:在支持 IPv6 的网络下打开任意一个「DNS 泄漏测试」网站,看返回的 DNS 服务器列表里是否混进了 ISP 的地址;根治办法要么在旁路由上把 IPv6 的 RA/DHCPv6 也接管过来统一下发 AdGuard 地址,要么在还没理顺之前干脆临时禁用内网 IPv6。

⚠️ 避坑 · 浏览器自带 DoH,绕过你的路由器

Firefox 和 Chrome 都内置了「安全 DNS / Secure DNS」开关,默认会把 DNS 查询直接送到浏览器自己配置的 DoH 服务商(常见是 Cloudflare 或 Google)——走的是 443 端口,和普通网页流量长得一模一样。这意味着就算你在旁路由上把 53/853 全部收编进 AdGuard,浏览器依然可能完全无视你的设置,自己另开一条加密通道直连上游,AdGuard 在这条请求上完全「失明」,广告过滤也就对这部分流量失效了。应对办法:要么在浏览器设置里手动关掉内置的 Secure DNS(或指向你自己的 AdGuard DoH 地址),要么让 AdGuard Home 识别并阻断已知的公共 DoH 服务商域名。

📌 本章要点
  • DNS 的本质是把「人记名字」翻译成「机器认地址」,靠的不是一本大账本,而是根 → TLD → 权威的分层责任链(RFC 1034/1035)。
  • 你和递归解析器之间是递归查询(一次搞定);解析器和根/TLD/权威之间是迭代查询(一跳跳转介),别把两者搞反。
  • 根服务器「13 个」源自 512 字节 UDP 包限制的历史遗留(留有安全余量,并非精确卡限),现代靠 anycast 把 13 个名字撑出了上千台物理实例。
  • dnsmasq是转发器+缓存+DHCP,AdGuard Home是过滤代理,二者抢 53 端口是真实存在的坑;本会话用 server=127.0.0.1#5335 让 dnsmasq 把普通查询转发给监听在 5335 的 AdGuard 解决。
  • 明文 DNS 在 HTTPS 建立前就暴露了域名;DoT(RFC 7858,853 端口)和DoH(RFC 8484,443 端口)把这段加密,但换来的是「易管控」和「难拦截」两种取舍,DoH 加密不等于 DNSSEC 验真。
  • 再干净的过滤链路也挡不住两个洞:IPv6 DNS 泄漏(RA 下发的 IPv6 DNS 绕过你的过滤器)和浏览器自带 DoH(直接绕开路由器另开加密通道)——两个都要单独核查、单独关掉。
