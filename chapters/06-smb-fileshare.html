为什么复制一个文件要牵出这么多协议 —— 发现、权限、语义三道坎

「把文件从设备 A 传到设备 B」这句听起来最简单的操作,拆开看至少要回答三个子问题:A 怎么在网络里发现 B?A 有没有权限读写 B 的文件系统?不同操作系统的文件语义(大小写、权限位,以及 macOS 独有的「资源叉」)要怎么对齐?本章要讲的三套方案——SMB/Samba、AirDrop(AWDL)、LocalSend/PairDrop——分别用完全不同的方式回答这三个问题,谁也不是谁的「升级版」,只是取舍不同。

SMB/CIFS —— 局域网里最古老的通用语

SMB(Server Message Block)最早由 IBM 的 Barry Feigenbaum 于 1983 年设计,跑在 NetBIOS 之上,用来在局域网里共享文件和打印机。微软接手后不断扩展协议,一度把它更名为 CIFS(Common Internet File System)——今天这两个名字仍在很多地方混用,指的基本是同一件事。

SMB 1.0 用 16 位字段描述数据大小,单次读写的数据块上限只有 64KB,而且协议非常「啰嗦」(chatty):完成一次文件操作要在客户端和服务器之间来回打好几轮招呼,在跨广域网或高延迟链路上体验很差。2006 年微软随 Windows Vista / Windows Server 2008 推出 SMB 2.0,砍掉了 64KB 块上限、减少了握手往返次数;此后每一代大版本都在啃同一块骨头——更少的往返、更大的吞吐、更强的安全,演进历程如下表:

方言 / 版本首见于关键变化
SMB 1.0(CIFS)Windows NT / 9x 时代16 位字段,单块上限 64KB,握手往返多、协议「啰嗦」
SMB 2.02006 · Windows Vista / Server 2008去掉 64KB 块上限,精简命令、减少往返

展开:SMB1 为什么现在几乎被判「死刑」

SMB1 除了慢,还在 2017 年惹出过一次全球级安全事故:Windows SMBv1 服务器处理某些请求的方式存在一个缓冲区溢出漏洞(CVE-2017-0144,属于微软安全公告 MS17-010 一次性修复的 6 个相关 SMBv1 漏洞之一,EternalBlue 利用的正是这一个),攻击者不需要任何凭据,发一个精心构造的数据包就能在目标机器上以内核权限执行任意代码。这个漏洞被称为 EternalBlue,2017 年 4 月被 Shadow Brokers 黑客组织公开泄露后一个月内,就被武器化成了 WannaCry 勒索软件——像蠕虫一样扫描局域网里开着 445 端口(SMB 默认端口)的机器并自动传播,瘫痪了全球多家医院、企业和政府机构。微软后来的应对不是「再打个补丁」了事:从 Windows 10 Fall Creators Update(1709)和 Windows Server 2019 起,SMB1 客户端/服务器组件都改成了默认不安装的「可选功能」。这也是为什么有些老式扫描仪、NAS 只支持 SMB1 时,Windows 会直接找不到它——需要手动到「启用或关闭 Windows 功能」里勾选「SMB 1.0/CIFS 文件共享支持」才能连上,但这样做等于主动打开了当年那一类漏洞的攻击面,只应作为过渡方案。

不管协商到哪个方言,一次 SMB 会话都遵循同样的四段式骨架:先协商双方都支持的方言,再验证身份建立会话,再「挂载」到具体共享(这一步术语叫 Tree Connect,对应平时输入的 \\server\share),最后才谈得上打开、读、写文件。画成时序图是这样:

🎓 原理 · 有状态的会话协议

图 2 里的 Session ID、Tree ID 不是随手起的名字——SMB 是一个有状态(stateful)协议:服务器要在内存里记住「这个会话是谁登录的」「这个 Tree 对应哪个共享」「这个文件句柄现在锁着没有」,直到显式断开为止,有点像银行的专属服务窗口——柜员认得你,记得你上次办到哪一步,不用每次都重新自报家门。这和后面要讲的 HTTP/REST 这类无状态设计正好相反:无状态协议更像自助终端,每次操作都要重新插卡验证,不指望「记住你是谁」,而是把全部上下文塞进每一次请求里。(这里说的是协议模型:现代 SMB2/3 已经不需要 NetBIOS,直接跑在 TCP 445 端口上——上一节讲 SMB「跑在 NetBIOS 之上」,指的是 SMB1 时代的历史依赖,两处并不矛盾。)SMB 在五层协议栈里的位置、和 HTTP 这类应用层协议的异同,见第 10 章·计算机网络体系。

Samba —— 让 Linux 与路由器说 Windows 方言

Windows 自己实现 SMB 不奇怪,奇怪的是 Linux、路由器、NAS 怎么也能「说」SMB。答案是 Samba——一个开源、免费、把 SMB/CIFS 协议重新实现了一遍的软件包,今天几乎所有非 Windows 系统的文件共享能力都靠它。

Samba 的故事始于 1991 年底:时年在澳大利亚国立大学读博士的 Andrew Tridgell,用一个 packet sniffer(抓包工具)分析 DEC Pathworks 服务器的网络流量,一点点把协议逆向出来,写成了一个 Unix 版的文件服务器——他当时甚至没意识到自己实现的其实就是 NetBIOS/SMB 协议。项目起初连名字都没有;后来因为商标冲突不能叫「smbserver」,Tridgell 索性用 grep -i 's.*m.*b' /usr/dict/words 在系统字典文件里搜「依次包含 s、m、b 三个字母」的单词,搜出来的候选有 salmonberry、samba、sawtimber、scramble 四个,「Samba」是其中最顺耳、最好记的选择。今天的 Samba(4.x 系列)不只是文件服务器,还能扮演 Windows Active Directory 域控制器,协议上支持到最新的 SMB 3.1.1。

🛠 实战锚点 · 旁路由变身 NAS

第 02 章把 Chromebox 刷成 iStoreOS 当旁路由(192.168.1.2)之后,插一块 USB 硬盘、装上 luci-app-samba4,就能在后台配出一个 SMB 份额——背后跑的正是 Samba 的 smbd。一段典型配置:

[nas]
    path = /mnt/sda1/share
    read only = no
    guest ok = no
    valid users = mediauser

guest ok = no 意味着必须用账户密码登录——第五节会看到,这在 Win11 上几乎是唯一选项。

vfs_fruit —— 给 Samba 装上苹果翻译官

SMB 协议本身描述的是「文件名 + 字节流 + 权限位」这套 Windows/Unix 通用语义,完全没有 macOS 独有的东西:resource fork(资源叉,老 Mac 系统遗留的「文件的第二份数据」,用来存图标、类型信息等)、大量自定义扩展属性(xattr),以及 Finder 依赖的一套 AAPL 协商扩展。普通 Samba 份额面对 macOS 客户端能用,但会有各种别扭——比如没法当 Time Machine 备份盘,复制文件到 Finder 里还会时不时冒出影子文件。

vfs_fruit 是 Samba 的一个 VFS(虚拟文件系统)模块,专门补上这一课:它会拦截 macOS 客户端发起的 AAPL 协议协商,把资源叉/扩展属性映射成 Samba 能存储的格式(原生 stream 或 AppleDouble 影子文件二选一),还能让分享出来的目录被 Time Machine 认作合法备份卷。这些映射最终都要落到 Samba 主机的本地文件系统上,不同文件系统(ext4/exFAT/NTFS)对扩展属性的支持程度不同,直接决定这套翻译好不好用,细节见第 07 章·文件系统。

SambaWiki 给出的推荐配置大致是:

[global]
    vfs objects = fruit streams_xattr
    fruit:metadata = stream
    fruit:model = MacSamba
    fruit:veto_appledouble = no

[TimeMachineBackup]
    path = /mnt/sda1/timemachine
    fruit:time machine = yes
⚠️ 避坑 · Finder 写出的垃圾文件

如果 vfs objects 没加 fruit,直接把 Samba 份额当成 Mac 的普通网络盘用,Finder 为了模拟资源叉和元数据,会在每个目录里悄悄生成一堆 ._原文件名 和 .DS_Store。这些文件在 Windows/Linux 那边全是无意义的垃圾,还可能把只认「文件名前缀」的老程序绊倒。根治办法只有一个:在服务端启用 vfs_fruit,把这层翻译工作交给 Samba 自己做,而不是指望 macOS 客户端单方面应付。

Win11 焊死的大门 —— guest 访问与映射网络盘

Windows 10 Enterprise、Pro for Workstations 与教育版从一开始就不允许「来宾账户回退」——就算对面的服务器主动提出「你可以用 guest 身份登录」,这几个版本的 Windows 客户端也会拒绝;但普通消费版的 Windows 10 Home/Pro 默认其实还留着口子,允许回退到 guest。到了 Windows 11(Pro Insider Preview build 25267 及之后的正式版——微软文档目前明确点名的是 Pro,未见到 Home 在同一 build 上被同等收紧的官方说法),guest 登录默认同样被拒绝。

原因很直接:guest 登录不支持 SMB 签名和加密,攻击者可以伪造一台「看起来很正常」的共享服务器,诱导用户无感登录后投递恶意文件。Windows 11 24H2 的 Enterprise、Pro 与教育版更进一步,默认强制要求 SMB 签名(Home 版被微软文档明确排除在这条默认强制之外,仍不要求签名),连带着让一些老旧 NAS、扫描仪之类只支持「裸连」的设备在这几个版本上直接连不上——这背后的密码学原理(签名、哈希、证书)见第 15 章·密码学与网络安全。

🛠 实战锚点 · 映射网络驱动器

把旁路由(192.168.1.2)的份额变成一个盘符,图形界面走「此电脑 → 映射网络驱动器」,命令行等价于:

net use Z: \\192.168.1.2\nas /user:mediauser 你的密码 /persistent:yes

/persistent:yes 让这个映射开机自动重连;不带用户名密码直接连、指望它照老办法回退到 guest,在 Win11 上现在只会换来下面这条报错。

⚠️ 避坑 ·「你的组织的安全策略阻止未经身份验证的来宾访问」

给旁路由配的 Samba 份额如果留了 guest ok = yes,Win11 弹出的正是这条错误。修复只有两条路:① 老老实实在 Samba 端建一个真实账户(推荐,上一节的 valid users = mediauser 就是这么来的);② 用组策略(gpedit.msc → 计算机配置 → 管理模板 → 网络 → Lanman 工作站 → 启用不安全的来宾登录)或 PowerShell 强行放行:

Set-SmbClientConfiguration -EnableInsecureGuestLogons $true -Force

微软自己的文档也明说这会让客户端暴露在中间人攻击和凭据窃取之下,能不开就不开——2017 年的 WannaCry 就是前一节讲的 SMB1 漏洞教训,收紧 guest 访问是同一条治理思路的延续。

AirDrop 为什么点不出来 —— AWDL 内幕

既然 SMB 已经能跨平台、Samba 也免费,为什么 iPhone 传张照片给 Windows 笔记本还是做不到「AirDrop 一下」?答案是 AirDrop 压根没有走 SMB 这条路——它建立在 AWDL(Apple Wireless Direct Link)之上,而 AWDL 是苹果一家的专有协议,从未公开完整规范。

AWDL 大约在 2014 年随 iOS 7 引入,表面上基于 802.11(也就是 Wi-Fi)的物理层,但协议行为完全是苹果自定义的:设备平时正常连着家里的 Wi-Fi 路由器,同一张网卡会周期性短暂跳离当前信道,跳到一个「社交信道」(social channel,常见是 6/44/149)上和附近的苹果设备互相同步、选出一个「主时钟」设备;确认要传输后,双方再协商一个私有数据信道完成真正的文件传输,然后跳回原来的 Wi-Fi 信道。这套「一边正常连着家用 Wi-Fi,一边周期性抽个空跟附近苹果设备打招呼」的行为,有点像开车时眼睛始终盯着前方,却会习惯性地快速瞥一眼后视镜确认后车是谁——那一瞥足够短促,不会真的耽误正常开车。发现阶段还叠加了一层 BLE(低功耗蓝牙)广播,负责在「隔空投送」界面上「看到」附近的设备;真正的大文件搬运才交给 AWDL,数据本身还套了一层 TLS 双向证书认证,不是完全裸奔。

这也是 Windows/Android 做不出原生 AirDrop 的根本原因:不是「不想做」,而是 AWDL 的协议细节从未公开,连支持它需要的信道跳频时序都要靠无线网卡驱动配合——没有授权、没有规范,第三方连逆向都费劲。

🔎 深挖 · OWL 与 Wi-Fi Aware

德国达姆施塔特工业大学的 SEEMOO 实验室在 2018 年前后逆向出了一套开源实现,叫 OWL,证明 AWDL 并非不可破解,只是工程量很大、苹果也没有义务配合。真正的转折点来自监管:欧盟《数字市场法》(DMA)裁定苹果必须向第三方开放互操作性。苹果的回应不是开放 AWDL 本身,而是拥抱 Wi-Fi Aware——一个由 Wi-Fi 联盟(Wi-Fi Alliance)主导、基于 IEEE 802.11 的公开点对点标准。2025 年 6 月的 WWDC25 上,苹果宣布向第三方开发者开放 Wi-Fi Aware 框架;随同年 9 月发布的 iOS 26,这个框架已经在全球范围正式上线(不限于欧盟市场)——第三方开发者现在就能用它做出跨 iPhone/Android 的「隔空投送」替代品。跨平台文件直传最终得以实现,靠的不是逆向,而是标准化。

开源补位 —— LocalSend 与 PairDrop

在 AWDL 被彻底解决之前,开源社区已经用另一条更朴素的路径填上了这块拼图——不去抢占专有射频协议,而是老老实实站在「每台设备都有」的标准 IP 网络上,重新做一遍「发现 + 传输」。

LocalSend 是一个原生跨平台 App(Windows/macOS/Linux/Android/iOS),设备发现靠 UDP 组播:各设备在 53317 端口周期性广播一条「我在这里」的公告,收到公告的一方再用 TCP 连回去交换设备信息(TCP 失败就退化成 UDP 应答)。真正的文件传输走 HTTPS:每台设备现场生成一份自签 TLS 证书,发送方依次调用 /api/v2/register、/api/v2/prepare-upload、/api/v2/upload 几个 REST 接口把文件流式传过去,过程中可以加一道 PIN 码确认。

PairDrop 走的是另一个极端——不装 App,浏览器打开网页就能用(它 fork 自更早的 Snapdrop 项目)。信令(告诉两台设备「该互相连谁」)走 WebSocket,真正的文件数据走 WebRTC 的点对点数据通道;如果双方在同一局域网,数据基本不经过服务器中转。它还比 LocalSend 多一层「配对」能力:用 6 位数字码或二维码「记住」一台设备,以后隔着不同网络也能重新连上;或者用 5 位字母码进一个临时「公共房间」,跨公网、NAT 后面也能传(靠 TURN 服务器中转兜底)。

把这两者和前面的 SMB、AirDrop 放在一起看:SMB 用账号体系换来了「随时挂载」的持久性,AirDrop 用专有射频换来了极致的易用和速度,LocalSend/PairDrop 则放弃了这两样极致,换来了「只要有网页或装个 App,什么系统都能连」的普适性——三种取舍,没有绝对的优劣,只看你要解决的是哪个场景。

📌 本章要点
  • SMB/CIFS 是局域网文件共享的「通用语」,1983 年由 IBM 设计,微软主导演进;SMB2(2006)去掉 64KB 块上限,SMB3(2012 起)带来 Multichannel、加密和 RDMA,SMB 3.1.1(2015)强制预认证完整性防降级攻击。
  • Samba 是 SMB 协议的开源实现,1991 年由 Andrew Tridgell 逆向 DEC Pathworks 协议起家,今天让 Linux/路由器/NAS 都能说「Windows 的语言」。
  • vfs_fruit 是 Samba 面向 macOS 的翻译层,补上资源叉、扩展属性、Time Machine 支持——不装它,Finder 会在份额里留下一堆 ._ 开头的垃圾文件。
  • Windows 10/11 的 Enterprise/Pro/教育版默认禁止 SMB 来宾登录,Win11 24H2 起这些版本还强制 SMB 签名(Home 版是例外,两项都不强制);这是为了堵住「伪造服务器诱导免密登录」这类攻击面(WannaCry 就是 SMB1 漏洞的教训)。
  • AirDrop 建立在苹果专有的 AWDL 协议之上(BLE 发现 + AWDL 信道跳频传输 + TLS 认证),协议从未公开,这是 Windows/Android 做不出原生 AirDrop 的根本原因;在欧盟监管压力下,iOS 26 已经上线开放的 Wi-Fi Aware 标准,第三方开发者现在就能做出跨平台的「隔空投送」替代品。
  • LocalSend(HTTPS + UDP 组播)和 PairDrop(WebRTC + WebSocket 信令)用标准 IP 网络重新实现了「发现 + 传输」,牺牲部分速度换来了真正的跨平台。
