为什么复杂度决定成败

设想一个具体问题:在 100 万条记录里找一条。如果数据是随手堆放的一堆(比如一份没排序的列表),你唯一能做的是从头到尾挨个比对——最坏情况要看完全部 100 万条,这叫线性查找,记作 O(n)。但如果数据先排好了序,你可以每次只看中间那条、比它大就去右半边、比它小就去左半边——这是二分查找,每一步排除掉一半候选,最坏只要 log₂(1,000,000)≈20 步。同一个问题,只因为"数据有没有排好序 + 用哪种查法",答案要走的步数差了 5 万倍。

数据结构与算法研究的正是这两件事:数据结构决定"数据怎么摆"(排好序的数组?串起来的链表?分层的树?哈希表?),算法决定"步骤怎么走"(怎么查、怎么排、怎么遍历)。程序"看起来卡"还是"感觉秒开",很多时候不是硬件不够快,而是背后选错了摆法或走错了步子——后面每一节都会回来印证这句话:03 章 AdGuard 秒判黑名单、10 章交换机秒转发、16 章 Git 秒查提交历史,都是本章原理的真实落地。

Big-O:量出"快慢"的尺子

Big-O 记号回答的不是"这段代码几点跑完",而是"如果输入规模翻倍,耗时大概涨几倍"——它衡量的是增长趋势,不是秒表读数。类比一下:问一辆车"这段路要开多久"是问具体耗时;问"如果距离翻倍,时间会不会也差不多翻倍"才是问增长趋势,而后者才是 Big-O 真正回答的问题。

🧭 原理 · Big-O 的形式化定义

"f(x) = O(g(x))" 的严格定义(维基百科)是:存在一个正实数 M,使得对足够大的 x,都有 |f(x)| ≤ M·|g(x)|。翻译成人话:只要能找到一个"放大倍数" M,让 g(x) 放大后从某个点开始永远盖住 f(x),就说 f(x) 是 O(g(x))。关键是"存在这样的 M"这件事本身,M 具体是多少无所谓——这也是为什么 O(2n) 和 O(n) 被视为同一复杂度:常数倍数在 Big-O 里被直接忽略。

复杂度还分最好情况(best case)、平均情况(average case)、最坏情况(worst case)——比如插入排序如果输入已经是正序的,每插入一个新元素只需和前一个比一次就知道不用挪动,几乎不做搬移(最好情况 O(n));但如果完全逆序,每个新元素都要一路搬到最前面(最坏情况 O(n²))。工程上做容量规划时,通常按最坏情况留余量,因为线上系统扛不住"运气不好就崩"。

🧩 类比 · 搬家:趟数重要,但"点箱子"本身也要花时间

把 n 想象成要搬的箱子数。笨办法是每次扛一箱来回跑,跑的趟数、花的总时间都随箱子数 n 线性增长,O(n);如果箱子实在太多,先花时间把箱子按房间分类、规划一条顺路的搬运路线,能让往后每一趟带得更有效率,长期看更划算——这类"先多想一步、换取整体更平缓的增长曲线"的思路,是不少更聪明的算法愿意多花的力气。

但"分类、规划路线"这一步本身也要花固定的时间——如果统共只搬 3 箱东西,直接扛着跑 3 趟,通常比先坐下来规划半天更快。这正是 Big-O 容易被误读的地方:它只承诺"箱子数量足够多之后,谁的增长趋势更平缓",不承诺"任何规模下都更快"。本章后面"工程视角"会提到,不少语言的内置排序在待排序片段很小时会主动切换成插入排序,原因和"3 箱东西不值得先规划路线"是同一个:O(n log n) 相对 O(n²) 的优势要等数据量爬过一个门槛才会显现,不是在任何规模下都成立的绝对排名。

复杂度名称典型例子
O(1)常数哈希表按 key 查值、数组按下标取值
O(log n)对数二分查找、平衡树查找 / 插入
O(n)线性遍历数组一次、线性查找
O(n log n)线性对数归并排序、堆排序、大多数语言内置排序
O(n²)平方冒泡 / 插入 / 选择排序、朴素两层嵌套循环
O(2ⁿ)指数穷举所有子集(n 个元素有 2ⁿ 个子集)

线性结构:数组·链表·栈·队列

最基础的地基结构是把数据排成"一条线"。最常见的两种实现方式——数组(array)和链表(linked list)——表面上都能存一串数据、都能遍历,但底层内存布局完全不同,导致优劣完全反过来。

数组 vs 链表:同样是"一条线",内存长得不一样

数组把元素挨个存在一整块连续内存里,访问下标 i 时直接用公式「地址 = 起始地址 + i × 单个元素大小」一步算出目标地址,是 O(1);但往中间插入一个元素,后面所有元素都要往后挪一位腾位置,最坏是 O(n)。链表反过来:每个节点各自散落在内存的任意角落,靠"指针"记住下一个节点在哪;只要已经拿到了插入点前一个节点的引用,插入/删除本身只是改几个指针,是 O(1),但要"找到"那个节点没法直接跳,只能从头一个个顺着指针走,是 O(n)。

🧭 原理 · 维基百科怎么说

"insertion in a dynamic array at random locations will require moving half of the elements on average"(维基百科 Linked list 词条)——数组插入的平均代价是移动半数元素。该词条还指出:"Sequential access on arrays and dynamic arrays is also faster than on linked lists on many machines, because they have optimal locality of reference and thus make good use of data caching."——数组的缓存局部性(cache locality)天然优于链表。

⚠️ 避坑 · 同样标着 O(n),实测可能差十倍

Big-O 只看增长趋势,不看常数因子——而"常数因子"在数组和链表上天差地别。CPU 从内存读数据是按缓存行(cache line)整块搬运的,数组元素紧挨着存,读一个顺带把后面几个也搬进了缓存(命中率高);链表节点散落各处,几乎每跳一个指针都要重新访问内存,一次次缓存未命中(cache miss)。这就是为什么理论上"同是 O(n) 遍历",数组遍历在真实机器上常常比链表快数倍——这背后是12 章要讲的存储层次问题。

栈(Stack)与队列(Queue):两种"排队规则"

栈和队列都是"只能从固定的一端/两端进出"的线性结构,区别在于规则:栈(Stack)是后进先出(LIFO, Last In First Out),像一摞叠起来的盘子,只能从最上面拿、最上面放;队列(Queue)是先进先出(FIFO, First In First Out),像排队买奶茶,先来的人先被服务。两者的核心操作(入栈/出栈 push/pop,入队/出队 enqueue/dequeue)都是 O(1)。

🛠 实战锚点 · 你天天在用它们

程序崩溃时打印出来的那一长串调用记录——调用栈(call stack)——就是一个真实的栈:函数 A 调用 B、B 调用 C,C 出错时,栈从顶部往下正好是 C→B→A 的调用顺序;08 章任务管理器里排队等 CPU 时间片的进程、以及打印机的打印队列,都是货真价实的队列结构。

💡 场景 · 递归函数为什么会"爆栈"

写一个不设终止条件(或者终止条件写错)的递归函数,跑起来往往不是死循环卡住,而是很快报错退出——Python 抛 RecursionError: maximum recursion depth exceeded,Java 抛 StackOverflowError,C/C++ 这类没有运行时兜底的语言甚至可能直接段错误(segmentation fault)崩溃。原因就在上一段"调用栈是一个真实的栈"里:每多一层函数调用,栈上就要多压一帧(保存这层函数的局部变量、返回地址等信息),而调用栈能用的内存空间是有限的——不是可以无限叠高的一摞盘子,是叠到房顶就会塌的一摞盘子。递归迟迟不返回,就是不停往这摞盘子上加,加到触顶,程序只能报错退出。

这也是为什么"能用循环就不硬上深递归"是工程上的常见取舍:循环靠一个变量反复更新,不额外占用调用栈空间;递归写起来更贴近数学定义、更好懂,但每一层都有真实的内存代价。真需要深递归时,常见做法是把遍历改造成显式用一个栈/队列模拟(把原本交给调用栈隐式做的事自己接管),或者查清楚所用语言/运行时是否支持"尾调用优化"这类机制——但这类优化在不同语言间支持并不一致(比如主流 Python 实现就没有),不能默认所有语言都有。

树:层级结构、二叉搜索树与堆

现实里很多数据本来就是"一层层"的,而不是"一条线"——公司组织架构、文件目录、家谱都是如此。树(tree)就是给这种层级关系建模的结构:一个根节点(root),每个节点可以有若干子节点(children),没有子节点的叫叶节点(leaf)。07 章里 ext4/NTFS 的目录结构、03 章里"根 → 顶级域(TLD)→ 权威服务器"的 DNS 解析路径,本质上都是树。

二叉搜索树(BST):靠一条不变的规则换来 O(log n)

二叉搜索树(Binary Search Tree, BST)在树的基础上加一条硬规则:对任意节点,左子树所有值都比它小,右子树所有值都比它大。这条规则让查找可以像二分查找一样,每比较一次就排除掉一整棵子树,理想情况下是 O(log n)——这正是开篇"100 万条记录、log₂(1,000,000)≈20 步"那套二分查找逻辑的同一种"比较一次、砍掉一半"打法,只是砍的对象从有序数组换成了树。

🧭 原理 · 维基百科的警告

"the worst case for BST search is O(n) where n is the total number of nodes in the BST, because an unbalanced BST may degenerate to a linked list."(维基百科 Binary search tree 词条)——如果插入顺序恰好是从小到大或从大到小,BST 会一路只往一侧长,退化成一条链表,查找也退化成 O(n)。这正是为什么工程实践里几乎不用"裸" BST,而是用 AVL 树、红黑树等自平衡树,靠插入/删除时自动"调整形状",把树高强制维持在 O(log n)。

⚠️ 避坑 · 有序数据"从小到大"插入 BST 是反面教材

把 1,2,3,4,5 依次插入一棵普通 BST,得到的不是矮胖的树,而是一条只往右长的链——查找退化成 O(n),等于白建了一棵"树"。数据库索引、文件系统目录(07 章)几乎都用 B 树 / B+树而不是普通 BST,原因之一就是它们天然抗这种退化,并且更贴合磁盘按块读写的特性。

延伸:AVL 树、红黑树、B 树——一句话区分
  • AVL 树:每个节点严格维持左右子树高度差 ≤1,查找最快,但插入 / 删除时"再平衡"开销较大。
  • 红黑树:允许更松的平衡(用红/黑染色规则代替严格高度差),插入 / 删除更便宜,C++ std::map、Java TreeMap 底层都是它。
  • B 树 / B+树:每个节点能装下不止 2 个子节点(通常几十到几百个),专为"按块读写"的磁盘 / SSD 设计,大幅降低访问深度——数据库索引和文件系统目录首选它。

堆(Heap):只关心"最大/最小是谁"

如果只关心"当前最大/最小是谁"而不需要完整排序,没必要维持整棵有序树——堆就是为这类需求量身定制的结构。堆是一种特殊的完全二叉树:最大堆(max-heap)里每个父节点的值都不小于它的子节点(根节点永远是最大值),最小堆(min-heap)反过来。堆最巧妙的地方是可以直接用数组存,不需要真的建指针:下标 i 的节点,左子节点在 2i+1、右子节点在 2i+2、父节点在 ⌊(i-1)/2⌋——纯算术定位(见图 3 右侧)。

🧭 原理 · 堆的复杂度

维基百科 Heap (data structure) 词条给出二叉堆的标准复杂度:取最大 / 最小值 Θ(1),插入、删除最大 / 最小值都是 Θ(log n)。这组复杂度是优先级队列(priority queue)的标准实现——"每次都要拿到当前最紧急的那个",是堆最典型的应用场景。

🛠 实战锚点 · 操作系统调度器的原型

11 章会讲到,操作系统调度器要频繁回答"下一个该给哪个进程分时间片";如果每次都把所有进程扫一遍找优先级最高的是 O(n),规模一大就扛不住。用堆实现的优先级队列,插入一个新进程、取出优先级最高的都是 O(log n)——这正是很多调度器内部数据结构的原型。

图:万物皆关系

树要求"每个节点只能有一个父节点",但现实里很多关系并不服从这条规矩——社交网络里 A 认识 B、B 也认识 A;道路网里一个路口连着好几条路;10 章里"笔记本 → 旁路由 → 主路由 → 目标服务器"那条链路,本身也只是更大网络拓扑图里的一小段。这些场景需要更宽松的结构:图(graph)——由节点(vertex)和连接节点的边(edge)组成,边可以有方向(有向图)也可以没方向(无向图)。

两种存法:邻接表 vs 邻接矩阵

表示法空间复杂度判断"两点间是否有边"适合场景
邻接矩阵 adjacency matrixO(V²)O(1)图较稠密、常需要"是否直连"
邻接表 adjacency listO(V+E)最坏 O(V)图较稀疏(真实世界的图多数如此)

(V = 节点数,E = 边数。)现实世界的图几乎都是稀疏图——一个人认识几百人,不是认识全世界 80 亿人——所以工程上绝大多数场景用邻接表。

遍历:BFS 与 DFS

广度优先搜索(BFS, Breadth-First Search)借助队列,一层一层向外扩散,天然适合求"无权图最短路径";深度优先搜索(DFS, Depth-First Search)借助栈(或递归调用栈)一条路走到黑再回退,适合判断连通性、检测环、拓扑排序。用邻接表实现时,两者的时间复杂度都是 O(V+E)——每个节点访问一次、每条边检查一两次;如果换成邻接矩阵,复杂度会退化到 O(V²),因为每个节点都要把整行 V 个格子扫一遍才能找出它的邻居。

🔍 深挖 · Git 的提交历史就是一张图,不是树

Git 官方术语表把这件事写得很直白:"The commit objects form a directed acyclic graph, because they have parents (directed), and the graph of commit objects is acyclic"(git-scm.com gitglossary)。每个提交对象内部存的是"我的父提交是谁"的指针;普通提交只有 1 个父提交(看起来像树),但合并提交(merge commit)会同时指向两个父提交——这一个节点两个"父指针"的场景,正是图和树的本质分界线:树里每个节点只能有一个父节点,图不做这个限制。16 章会展开讲 Git 内部这套对象模型。

🛠 实战锚点 · 路由选路也是图论问题

10 章里路由器靠路由表做"最长前缀匹配"选路,再往底层看,像 OSPF 这类路由协议本质是在一张"设备是节点、链路是边"的图上跑最短路径算法(Dijkstra 算法的直系应用——Dijkstra 用优先级队列每次贪心弹出当前已知最短距离最小的未访问节点,是堆在图论里的经典落地)——网络拓扑的"选路"问题,从数据结构视角看,一直都是图论问题。

哈希表:用空间换时间的 O(1) 魔法

前面树结构最好也只能做到 O(log n)——因为它始终要"比较"着往下走。哈希表(hash table)换了个思路:不比较,直接算。给定一个 key,用哈希函数(hash function)算出一个下标(哈希值,也叫哈希码),直接跳到那个下标去存 / 取——只要哈希函数够好,不管表里有多少数据,查找的平均耗时几乎不随数据量变化。维基百科的说法是:"In a well-dimensioned hash table, the average time complexity for each lookup is independent of the number of elements stored in the table."(维基百科 Hash table 词条)

🧩 类比 · 图书馆怎么在几十万本书里几秒钟抽出一本

笨办法是从第一排书架开始一本本比对书名,直到翻到目标——这是线性查找 O(n);聪明一点的图书馆按书名拼音顺序把书排好,你可以像本章开头的二分查找一样,每次翻到中间判断目标在前半段还是后半段——这是 O(log n)。而按"首字母直接对应书架分区"摆放(A 区、B 区……),你几乎不用翻找、不用一路比较,拿到书名的第一个字就知道该冲向哪个分区——这才是哈希表的思路:哈希函数就是那条"字→分区"的换算规则,直接算出目标在哪,不需要一路比较着找。

冲突对应的场景也很好想:两本书名首字相同的书,理应挤进同一个分区——图书馆的解法是把它们紧挨着排在一起,翻到这一小片后再一本本比对着找。哈希表的链地址法本质上是同一件事,只是"紧挨着排"的手段换成了链表:先靠哈希函数一步跳到对应坑位,再在那一小撮挂在同一坑位的元素里顺着链找完——比起完全没分区、从头找到尾,还是快了一大截。不过撞进同一分区的书太多时,这一小撮就不小了,查找也会跟着变慢。

冲突:两个 key 算出同一个坑怎么办

哈希函数的值域是有限的(比如表大小只有 8),但 key 可能有无数种,冲突(collision)——两个不同的 key 算出同一个下标——是必然会发生的,不是"运气差"。维基百科总结了两种主流解法:"Common strategies to handle hash collisions include chaining, which stores multiple elements in the same slot using linked lists, and open addressing, which searches for the next available slot according to a probing sequence."(维基百科 Hash table 词条)——即链地址法(separate chaining),每个坑位挂一条链表;开放寻址法(open addressing),冲突时按某种探测规则去找表里下一个空位。

worked example:给 02/03 章的三个真实名字建一张哈希表

用一个极简的哈希函数练一遍手感:hash(key) = (key 里所有字符的 ASCII 码之和) mod 8,表大小 m=8(坑位下标 0~7)。把02 章旁路由、03 章 DNS 链路里三个真实的名字塞进去:

hash("dnsmasq")  = (100+110+115+109+97+115+113)         mod 8 = 759 mod 8 = 7
hash("adguard")  = (97+100+103+117+97+114+100)           mod 8 = 728 mod 8 = 0
hash("istoreos") = (105+115+116+111+114+101+111+115)     mod 8 = 888 mod 8 = 0   ← 和 adguard 撞车了!
  1. 算哈希:三个 key 分别算出坑位 7、0、0——"adguard" 和 "istoreos" 落进了同一个坑位 0,这就是一次真实发生的哈希冲突。
  2. 发现冲突:坑位 0 已经被 "adguard"(值 5335,即 03 章 AdGuard 监听端口)占用,"istoreos"(值 192.168.1.2,即旁路由自身地址)必须想办法共存,而不是覆盖掉前者。
  3. 链地址法解决:坑位 0 挂一条链,先接 adguard,链表再接 istoreos;坑位 7 单独存 dnsmasq(值 53,03 章 dnsmasq 监听端口)。查 "dnsmasq" 时不用扫过其他 7 个坑位,直接算一次哈希跳到坑位 7 就拿到答案——这正是 O(1) 平均查找的真实样子。
🧭 原理 · 负载因子决定哈希表什么时候该扩容

负载因子(load factor)α = n/m(n = 已存元素数,m = 坑位数)是哈希表最关键的健康指标。维基百科给出两条具体的工程经验:链地址法通常在 α 介于 1~3 之间时性能最好;开放寻址法则"cannot have a load factor greater than 1",且"the performance of open addressing becomes very bad when the load factor approaches 1"(维基百科 Hash table 词条)——这也是为什么几乎所有语言内置哈希表(Python dict、Java HashMap)都会在 α 超过某个阈值时自动扩容、重新哈希。

⚠️ 避坑 · 哈希函数选不好,O(1) 会打回 O(n)

上面的示例哈希函数只是为了演示手算,现实里绝不能这么用——它对相似字符集的字符串很容易大量冲突。真正的哈希函数(如 MurmurHash、SipHash)追求"输入差一点、输出差很多"和"分布足够均匀"。如果哈希函数设计得差,或被恶意构造大量 key 让它们全部冲突到同一个坑位(哈希洪水攻击 hash flooding),链地址法的那条链会退化成一条长长的链表——查找从理想的 O(1) 打回现实的 O(n)。

🔍 深挖 · 哈希表的哈希 ≠ 密码学的哈希

本节的哈希函数只求"快、分布均匀",不要求"没法反推""不能故意造出两个不同输入撞同一个输出"。15 章会讲的 SHA-256 等密码学哈希函数,要求恰恰相反:必须几乎不可能反推原文、几乎不可能故意构造碰撞——这也是为什么 Git(16 章)拿 SHA 哈希值当对象的"身份证号"做内容寻址,而不是随手拿字符 ASCII 之和这种简易哈希:后者防不住任何人蓄意构造出两个内容不同但哈希值相同的文件。

排序:经典算法全家福

排序是数据结构与算法里最"古典"的问题,也是理解复杂度差异最直观的战场。经典比较排序按"笨办法 / 聪明办法"分成两大阵营:

算法最好平均最坏额外空间稳定?
冒泡排序 Bubble SortO(n)O(n²)O(n²)O(1)是
插入排序 Insertion SortO(n)O(n²)O(n²)O(1)是
选择排序 Selection SortO(n²)O(n²)O(n²)O(1)否
归并排序 Merge SortO(n log n)O(n log n)O(n log n)O(n)是
快速排序 QuicksortO(n log n)O(n log n)O(n²)O(log n)否
堆排序 HeapsortO(n log n)O(n log n)O(n log n)O(1)否

(数据来源:维基百科 Sorting algorithm 词条比较排序总表。)稳定(stable)指相等的元素排序前后相对顺序不变——比如先按姓氏排、再按班级排时,如果排序算法不稳定,同班级内本该保留的姓氏顺序可能被打乱,这在"多字段排序"场景下很关键。

归并排序 worked trace:分到底,再一路合并回去

归并排序是分治(divide and conquer)的典范:把数组切成两半,分别递归排好序,再把两个有序的半边"合并"成一个有序整体。跟踪一遍 [8, 3, 5, 1, 9, 2](就是图 2 数组示例里的那 5 个数,再加一个 2)的排序过程:

拆分(一路切到只剩 1 个元素):
[8,3,5,1,9,2]
 → [8,3,5]          [1,9,2]
 → [8] [3,5]          [1] [9,2]
 →     [3] [5]              [9] [2]

合并(两两合并回去,每次都保持有序):
[3] + [5]          → [3,5]
[8] + [3,5]        → [3,5,8]
[9] + [2]          → [2,9]
[1] + [2,9]        → [1,2,9]
[3,5,8] + [1,2,9]  → [1,2,3,5,8,9]   ← 完成

每一层"合并"都要扫过全部 n 个元素一次,总共有 log₂n 层,所以是 O(n log n)——而且不管输入多乱,这个数字都不变,这正是归并排序"最好/平均/最坏都是 O(n log n)"的原因,代价是需要 O(n) 的额外空间存合并结果。

🧭 原理 · O(n log n) 是比较排序的理论下限

维基百科给出一个更硬核的结论:比较排序(每一步只能"比较两个元素谁大谁小")存在一个数学证明的下限——至少需要 n·log n − 1.4427n + O(log n) 次比较。换句话说,不存在一种只靠"比较"的排序算法能稳定跑赢 O(n log n)——归并排序、堆排序已经摸到了这条理论天花板。

⚠️ 避坑 · 快速排序标称 O(n log n),最坏会退化到 O(n²)

快速排序平均性能通常是几种 O(n log n) 排序里最快的(常数因子小、原地排序),但如果每次选的"基准值(pivot)"恰好都是当前子数组里最大或最小的(比如输入本来就是正序 / 逆序,又选了固定位置的元素当 pivot,比如永远选第一个或永远选最后一个),每次划分只能排除 1 个元素而不是"劈成两半",退化成 O(n²)——这正是上表里快速排序"最坏"一栏单独标 O(n²) 的原因。现代实现通常用"随机选 pivot"或"三数取中"规避这种最坏情况。

🔍 深挖 · 复杂度不是纸上谈兵:一次实测的真实秒数

维基百科整理过一次实际测量(排序同一份数据,不同算法耗时):冒泡排序 128.84 秒、选择排序 58.34 秒、插入排序 50.74 秒、希尔排序 7.08 秒、堆排序 2.22 秒、归并排序 2.06 秒、快速排序(递归)1.22 秒(维基百科 Sorting algorithm 词条"Table of running times of popular algorithms";Lilith 计算机对 2048 个随机数排序的历史测量,重点看算法间的相对倍数而非绝对秒数)。冒泡排序和快速排序之间差了约 100 倍——这就是 O(n²) 与 O(n log n) 之间的理论差距,变成秒表上能读出来的真实数字。

亲手排一排:同一组数字,四种算法的比较/交换次数差多少

下面这个控件把前面表格里的冒泡、选择、插入、快速排序做成了柱状图动画:选一种算法点「开始」,柱子会一边比较一边交换,直到全部变绿(已就位),旁边同步统计比较次数和交换/移动次数。

切换算法、多跑几轮时,有几件事值得留意——它们把前面几节的结论串了起来:

  • 切换算法下拉框不会重新打乱数据(只有点「打乱」才会换一批新数字),所以可以在同一组数字上依次跑一遍冒泡、选择、插入、快速排序,做一次公平对比。这种对比下,快速排序的比较次数通常明显少于另外三种——O(n log n) 相对 O(n²) 的差距,在这里 30~50 个数的规模下已经用肉眼就能看出来,不用等到成千上万条数据才有感觉。
  • 冒泡排序和选择排序的比较次数只取决于数据个数 n,不管数据顺序如何都要扫完固定的次数;但两者的交换次数天差地别——选择排序每一轮最多只交换一次(总数不超过 n−1),冒泡排序的交换次数则等于数据里"顺序颠倒的数对"(逆序对)总数,数据越乱换得越多。比较次数和交换/移动次数是两个彼此独立的成本,这也是为什么某些对"写入"代价敏感的场景里,选择排序反而比看起来更聪明的算法更划算。
  • 插入排序是四个里唯一会视数据情况"提前收手"的——内层循环一旦找到该插入的位置就立刻停止比较,不会像冒泡、选择那样不管数据形状如何都扫完固定次数。它的"移动"计数,对应的正是前面"数组 vs 链表"一节说的"数组中间插入要搬动后面元素"那个 O(n) 代价,在这里你能看着它随数据形态实时变化。

提示:控件里的冒泡排序没有做「一轮零交换就提前退出」这个常见优化(上面复杂度表格「最好情况 O(n)」那一栏假设的是做了优化的版本),所以你会看到它和选择排序一样,比较次数固定是 n(n−1)/2,不随数据看起来多整齐而减少——真正会「看数据形状提前收手」的只有插入排序。

延伸:排序也能不比较——计数排序与基数排序

前面的理论下限只适用于"靠比较大小"的排序算法。计数排序(Counting Sort)换了个思路:如果知道数据全是整数、且取值范围不太大(比如 0~100 分的考试成绩),可以直接开一个长度为值域大小 r 的计数数组,统计每个值出现几次,再依次填回去——完全不需要"比较",复杂度是 O(n+r),值域够小时能做到接近 O(n)。基数排序(Radix Sort)则按位数(个位、十位、百位……)反复做稳定的计数排序,能处理更大范围的整数乃至字符串。二者都要求"数据结构已知、值域可控"这个前提,不是任意数据都能用。

工程视角:怎么选、怎么避坑

实际写代码时,极少需要自己从零实现这些结构——每种主流语言的标准库都已经提供了工业级实现(Python 的 list/dict/set,Java 的 ArrayList/HashMap/PriorityQueue,C++ STL 的 vector/unordered_map/priority_queue)。真正需要操心的,是按需求选对结构,以及认出隐藏在循环里的复杂度陷阱。

需求该用什么
按下标随机访问数组 / 动态数组(如 Python list)
频繁在中间插入 / 删除,且已经拿着位置引用链表
只在一端进出、后进先出栈
只在一端进出、先进先出队列
按 key 快速查值,不关心顺序哈希表(dict / HashMap / set)
需要有序遍历或范围查询平衡树(TreeMap / B 树索引)
反复取"当前最大 / 最小"堆 / 优先级队列
建模"关系网络"、求最短路径 / 连通性图 + BFS / DFS / Dijkstra
一次性把一批数据排好序直接调用内置 sort,不必手写
⚠️ 避坑 · 循环里写 if x in a_list 是最常见的隐藏 O(n²)

在一个长度为 n 的循环里,对一个 Python list 做一次 in 成员判断是 O(n)(要线性扫描);如果这个判断本身又被套在一个长度也是 n 的外层循环里,总复杂度悄悄变成了 O(n²)——代码"看起来"只是一层循环加一个条件判断,行为上却是两层嵌套。把里层判断换成 set 或 dict 的 in(平均 O(1)),总复杂度就能压回 O(n)。这是新手到中级工程师之间最常见的一道复杂度分水岭。

🔍 深挖 · 语言内置排序不是"随便选一个算法"

前面表格之外,维基百科对 Introsort 的注解是"Performs a combination of Quicksort, Heapsort, and Insertion sort"(C++ STL 多个实现用它),对 Timsort 的注解是"Makes n−1 comparisons when the data is already sorted or reverse sorted"(Python、Java 用它)。工程实践里几乎不会二选一,而是取长补短:平时用快速排序的平均速度优势,数据量很小时切成插入排序减少开销,快要触发快速排序最坏情况时切换成堆排序兜底,已经有序的片段直接跳过——这正是"知道每种算法的复杂度边界"在生产代码里最终落地的样子。

📌 本章要点

复杂度(Big-O)量的是增长趋势、不是秒表读数,同一渐进复杂度下常数因子仍能差出数倍(12 章缓存局部性)。数组下标访问 O(1)、插入 O(n);链表正好反过来。树靠"每步排除一半"换来 O(log n),但不平衡会退化成 O(n)(07 章文件系统靠 B 树规避)。堆只求"当前最值",O(log n) 增删换 O(1) 取值(11 章调度器的原型)。图放宽了"只能一个父节点"的限制,邻接表 + BFS/DFS 做到 O(V+E)(16 章 Git 的 DAG,10 章路由选路)。哈希表不比较、直接算,平均 O(1),代价是要管好负载因子和哈希函数质量(15 章安全哈希是完全不同的另一套要求)。排序没有免费午餐:比较排序理论下限是 O(n log n),非比较排序能更快但要满足"值域已知且较小"这类前提。工程上最重要的技能不是背熟每种算法的实现,而是养成"看到嵌套循环就下意识估一下复杂度"的反射弧。
